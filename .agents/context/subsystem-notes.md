## Deployment (Render)
- **The Render instance restarts roughly every 5 hours, so any APScheduler `interval` job of ~5h or longer never fires (found 2026-09-19).** An interval trigger counts from the moment the job is *added*, i.e. from process start — so the process must survive a full interval for the job to run even once. Measured on the `aira-ai-5tfr` service: **39 restarts in the 7 days to 2026-09-19**, most gaps almost exactly 5h00 (01:39→06:39→11:43→16:44→22:00, day after day), plus deploys on top. These are *graceful* restarts (`Shutting down` → `Started server process` on the same instance id), with no OOM lines in the logs and the service on the paid `starter` plan — so it is platform-side recycling, not the app crashing, and not free-tier idle spin-down. Consequences found: `ad-insights-sync` at `hours=6` ran **4 times in a week** (Sep 14 09:00/15:00, Sep 15 00:01/16:58 — the only four windows with >6h uptime), and `token-health-check` / `number-quality-sync` at `hours=24` had **not run at all** since Sep 12. **Rule: keep every interval job well under ~4h, or move it to a Render Cron Job** (which does not depend on process uptime). To audit, grep the logs for `Scheduler started` (one per restart) and for `Run time of job "<name>" was missed by` — APScheduler logs that warning on the runs that *do* happen, so its absence means the job never fired. Fixed in `0e35b2f1` / `7aa8b710`.
- **Correction (2026-07-25): `autoDeploy` is `yes` on the `aira-ai-5tfr` web service as of this date** (confirmed via `mcp__render__list_services`) — contradicts the 2026-07-02 note below that it was `no`. It flipped back on at some point between those dates; **always check current state via `mcp__render__list_services` before assuming either way**, don't trust either historical note. When it's `yes`, a plain `git push origin main` deploys automatically within ~1-2 min — confirm via `mcp__render__list_deploys` (status `"live"`) rather than assuming a manual trigger is needed.
- **`autoDeploy` was observed `no` on the `aira-ai-5tfr` web service as of 2026-07-02**, contradicting the 2026-06-06 decisions-log entry "Render Auto-Deploy ON." Don't assume `git push origin main` puts a change live — check `mcp__render__list_deploys` for the actual live commit (status `"live"`) before verifying or debugging "why isn't my fix working in prod." Deploys were manual/API-triggered as of that date (see correction above — no longer current).
- **Forcing a redeploy without dashboard access**: `mcp__render__update_environment_variables` (merge mode, e.g. re-setting `FRONTEND_URL` to its current value) triggers Render to pull latest `main` and redeploy even with `autoDeploy: no` — this is the only MCP-available way to redeploy; there's no direct "trigger deploy" tool. The auto-mode permission classifier treats this as a shared-production-resource mutation and will block it until the user has explicitly said to proceed for that specific action.

## Local dev workspace (VSCode extension, 2026-07-25)
- **This workspace sometimes auto-commits AND auto-pushes working-tree changes to `origin/main` under the user's own git identity, without an explicit `git commit`/`git push`.** Observed directly: a session's file edits appeared as a real pushed commit (message literally `"changes"`, authored as the user) that a teammate (`keerthi-sarav`) then saw live and had to fix a test against. **Not reliable/guaranteed** — a later session in the same workspace made edits that stayed as plain uncommitted working-tree changes (`git status` showed them unstaged) and needed an explicit `git add`/`commit`/`push`. **Always run `git status` before assuming either way** — don't assume edits are safely local just because you didn't run `git commit` yourself, and don't assume they're already pushed either. If `git log --oneline -3` shows a suspicious generic `"changes"` commit you don't remember authoring, that's this mechanism, not a mistake.
- **Windows backend runtime (updated 2026-07-31)** — the obsolete dot-prefixed backend virtual environment has been removed. The repo has `backend/venv`; use its Windows activation command when it is healthy. In Codex Desktop, `python` is not on PATH, so repository scripts can be run with the bundled interpreter reported by `codex_app.load_workspace_dependencies`.
- **`npm run dev` fails outright in the Bash tool on Windows (2026-09-09).** The script is `NODE_OPTIONS=--no-experimental-vm-modules next dev` — POSIX env-prefix syntax, but npm shells out to `cmd.exe`, which reports `'NODE_OPTIONS' is not recognized`. Run the binary directly instead: `cd frontend && NODE_OPTIONS=--no-experimental-vm-modules ./node_modules/.bin/next dev`. Remember the `basePath` note above — the URL is `http://localhost:3000/aira/...`, not `/...`.
- **Kill dev servers properly, or they corrupt `.next` (2026-09-09).** Stopping a backgrounded `next dev` does not always reap the `start-server.js` child; it keeps holding port 3000 and the `.next` directory. Symptoms of the resulting mess: a fresh server silently binds 3001/3002/3003 while your curl to 3000 hits the zombie, then `Cannot find the middleware module`, `missing required error components, refreshing...`, and `ENOENT ... .next/cache/webpack/client-development/N.pack.gz` in the log. Recovery: list the listeners (`Get-NetTCPConnection -LocalPort 3000..3003`), confirm the command line is this repo's Next `start-server.js` child under `node_modules`, `Stop-Process -Force` them, `rm -rf frontend/.next`, then start one server. Deleting `.next` while a server still holds it is what causes the corruption in the first place — stop first, delete second.
- **To screenshot dashboard UI, render it on a throwaway route.** `middleware.ts` only guards `/dashboard`, and there's no Supabase session available in this harness, so `/dashboard/*` always redirects to `/login`. Copy the component/JSX into a temporary `frontend/app/<name>/page.tsx` (outside `/dashboard`), screenshot it with Playwright (`chromium.launch({ channel: 'chrome' })` — the bundled browser binaries are not installed, the system Chrome is), then delete the route **and** its generated `frontend/.next/types/app/<name>/` stub, which otherwise fails the next `tsc --noEmit` with `TS2307: Cannot find module`.
- **`frontend/.env.local`'s `NEXT_PUBLIC_SUPABASE_URL`/`NEXT_PUBLIC_SUPABASE_ANON_KEY` can silently drift from the live project** (found 2026-07-29: it pointed at a dead project ref that no longer resolves in DNS, while `backend/.env`'s `SUPABASE_URL` correctly pointed at the live `ayftynkgmfkaqmmnlmoc`). Symptom: operator/tenant login fails with `ERR_NAME_NOT_RESOLVED`/"Failed to fetch" in the browser console, or (if the vars end up empty) middleware throws "Your project's URL and Key are required to create a Supabase client." Don't try to reconstruct the values from memory or old files — `.env*` files are permission-denied to Read/Edit directly in this harness anyway. Instead pull them live: `mcp__claude_ai_Supabase__list_projects` → `get_project_url`/`get_publishable_keys` for the one live project, hand the three lines (`NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `NEXT_PUBLIC_API_URL=http://localhost:8000`) to the user to paste in, then restart `npm run dev` (env vars are read at process start, a running dev server won't pick up an edited `.env.local`).

## Broadcast delivery & retry
- **Delivery truth = `messages.delivery_status`** (+ `delivery_error_code`/`_title`), set by the delivery webhook (webhook.py ~L463-517). `broadcast_recipients.send_status` only reflects **Meta API acceptance** (returns message_id), NOT delivery — it's the WRONG signal for "did the lead receive it."
- **`send_status` stays `sent` on a delivery failure — on purpose (2026-09-17, `ee717904`).** The webhook used to try `send_status='delivery_failed'`, but `broadcast_recipients_send_status_check` (migration 166) only allows `sent/failed/rejected/opted_out_skip/aborted_skip`, so it was rejected every time (live: 0 such rows ever, vs 110 failed broadcast messages). It was **deleted, not enabled**: leads list (`leads.py`), re-engagement, the History tab and the `template_performance` SQL functions all treat `send_status='sent'` as "this lead was messaged" — relabelling would silently hide healthy leads over account-level errors like 131042. Don't reintroduce it; a guard test in `test_delivery_error_classification.py` fails if you do.
- **Per-send / per-broadcast attribution = `services/delivery_status.py` `nearest_record`/`nearest_status`** (the outbound `messages` row nearest in time, −2min/+10min). Used by all 3 sites (upload.py history+segment CSV, tags.py stats) so they never disagree. **NEVER** use max-priority-in-window (an adjacent broadcast's `sent` masks this one's `failed`) or any-failed-in-window (over-attributes).
- **`leads.whatsapp_undeliverable`** = sticky lead-level "is this number currently reachable" flag (resets on inbound + delivered/read receipt). Good for re-engagement skip; **WRONG for per-broadcast stats** (never reset per send).
- **Error codes:** `131049` = marketing cap ("healthy ecosystem engagement") — manifests async as a `failed` webhook OR a silent accepted-never-delivered; retry-worthy. `131026` = wrong number → set `whatsapp_undeliverable`, never retry. Transient set `{131049,131048,131056,130472}` does NOT set undeliverable.
- **Auto-retry removed (migration 170, 2026-08-11).** The feature described in migration 104 (per-broadcast retry toggle, `services/broadcast_retry.py`, retry timeline UI, `retry_enabled`/`retry_time`/`retry_max_attempts`/`retry_of`/`retry_attempt`/`retry_completed_at` on `scheduled_broadcasts`) is gone end-to-end — service deleted, routes/scheduler job removed, columns dropped live. `broadcast_recipients.extra_cols` (same migration 104) was kept — it's used on every send for template personalization, unrelated to retry despite sharing a migration. See `.agents/decisions/log.md`.
- **`fail_detail` is filled on both failure paths.** Send-time rejections: `broadcast_executor.py` via `_meta_error_detail()`. Webhook delivery failures: `webhook.py::_delivery_fail_detail()` (Meta `error_data.details` → `message` → `title`, prefixed `(#code)`, capped 300), written as its **own** UPDATE keyed on `meta_message_id`. Rows from before 2026-09-17 stay blank — the details text was never stored, so no backfill. The failed CSV's `fail_reason` (`delivery_failed:code:title`) is built at export time from `messages`, not stored.
- `broadcast_recipients.meta_message_id` (set at send time by `broadcast_executor.py` for every accepted send — verified live 2026-09-17) and `leads.whatsapp_undeliverable` exist in prod but were added manually — **no migration** in the repo. A fresh DB built from migrations alone would lack both.

## Scoring (`services/scoring_engine.py` v3, 2026-09-24)
- **No numeric score any more.** `_classify_segment()` asks the LLM for hot/warm/cold directly. The keyword bonus (`intent_delta`) and engagement bonus are deleted. `leads.score` is still written as a compat value (A=9, B=6, C=2, D=0) because of the DB CHECK and exports; the UI shows only the segment badge, and lists sort by segment then `last_inbound_at`. Rejection sentinel still gives immediate D (score 0) and bypasses the lock. Segment lock: upgrade immediate, **every** drop needs 2 consecutive confirmations (2-segment drops used to be immediate, so one "ok" could knock Hot to Cold).
- **Fixed definitions beat the tenant rubric.** `_SEGMENT_DEFINITIONS` (Hot = a buying step, Warm = interest without one, Cold = none) are in the prompt for every tenant; the tenant rubric only supplies business examples, and the prompt says definitions win on conflict. Old 1–10 five-band rubrics are converted in code by `convert_5band_rubric()` (keeps client wording) but **still score worse than a regenerated rubric** because their Hot lines tend to name topics ("personal problems") rather than buying steps; `ai_tune._rubric_prompt()` now forces buying steps into Hot.
- **Ad pre-filled text is hidden from the classifier**, not just labelled: the line becomes the bare `_AD_PREFILL_MARKER`. With the words visible, an ad reading "I want detailed guidance" was scored as the lead's own stated need.
- **Eval harness: `backend/evals/scoring/run_eval.py`.** Runs the live classifier (real LLM, 3 runs per chat) on hand-labelled chats: `golden_synthetic.json` (committed; real estate, dental, NEET coaching) and `golden_real.json` (29 real Astro Tamil chats, **gitignored** because it holds customer names/DOBs, so it exists only on the machine that made it). `--regen-rubrics` swaps in the current generator's rubrics. Results 2026-09-24: v3 before fixes 74% accuracy / 64% Hot precision; after, with tenant's own old rubric 88% / 76%; with regenerated rubrics 95% / 92%, 100% Hot recall, 0 unstable. **Run it before and after any change to the prompt, definitions or rubric generator.** Labels are Claude's, not yet reviewed by the operator.
- **`_REJECTION_PATTERNS` covers EN + Tamil + Tanglish + Hindi + Hinglish + Telugu + Kannada + Malayalam (2026-07-29).** EN list is phrase-shaped, not just "stop"/"not interested" — also message/msg/text/call variants ("don't message me", "stop calling"), "not needed"/"not required"/"no interest"/"leave me alone"/"remove my number". Tanglish "don't message/call" is a shape regex (`panna{1,2}(dh|th)(ee|e|i)nga`) because romanized spelling varies wildly in real chat (`pannadhinga` vs `pannadheenga` vs `pannathinga` all seen live) — if a real message with clear reject intent still lands as Hot/Warm instead of D, suspect an uncovered spelling variant here before anything else. Telugu/Kannada/Malayalam only have the 3 core native-script words each (not needed/stop/don't want) — **not native-speaker verified**, treat as best-effort until someone who speaks them reviews. Deliberately did NOT add bare "no need" (EN) — too generic, collides with benign hedges like "no need to worry".
- **Arc-scoring LLM is Gemini `gemini-3.1-flash-lite` as of 2026-07-29 (was Groq Llama 3.3 70B, commit `22979bc`).** Llama 3.3's officially supported languages don't include Tamil; live-verified the same byte-identical Tanglish opening message scoring 6/7/8 across three leads on Groq. Matches the 2026-07-18 `analyze_call` migration below — `conversation_compactor.py` also moved the same day, see decisions/log.md 2026-07-29. Fallback on failure = current arc, not hardcoded 5.
- **`_score_arc()`'s Gemini call silently failed on every invocation from the Groq→Gemini migration until fixed later the same day (2026-07-29)** — it carried over `max_tokens=4` from the old Groq code unchanged. Live-tested against the real endpoint with the actual production prompt: `gemini-3.1-flash-lite` returns an **empty string** at `max_tokens=4` every time; `max_tokens=6` and up return the real digit reliably. Every arc score computed in that window silently fell back to whatever score existed before — and the `arc_updated` flag / UI `⚡arc` badge fires regardless of whether the LLM call actually succeeded or silently fell back, so there was no way to tell the two apart from the UI. Fixed to `max_tokens=8`. **If arc ever looks frozen again despite fresh `⚡arc` badges, suspect a token-budget truncation before assuming the rubric is just reading the conversation as low-intent.**
- **Ad-prefilled CTWA messages are marked and down-weighted in the arc prompt.** `messages.via_ad_referral` (migration 150, 2026-07-29) is true when the inbound message arrived with Meta's `referral.source_type == "ad"` — i.e. it's the WhatsApp click-to-chat ad's own pre-filled CTA text, not something the lead composed. `_score_arc`'s conversation transcript prefixes those lines with `_AD_PREFILL_MARKER` (`[ad-prefilled entry message]`) and the prompt explicitly tells the LLM to score it as neutral first-contact (5-6), never as composed interest — otherwise Meta's own auto-fill wording (which can contain intent-sounding words like "detailed"/"urgent") would inflate the arc score. Leads from the same CTWA campaign send byte-identical opening text — don't mistake that for the lead's own words when investigating a scoring report.
- **Escalation/handover follow-up messages are similarly marked (2026-07-29).** A lead chasing an unresolved handover ("still no one contacted me", "when will they call") reads to the arc LLM as dismissive/frustrated and drags the score down even though the lead is still engaged — the frustration is about a stalled callback, not the product. Messages sent inside a `chat_handovers` open window (`opened_at` minus a 5-minute pre-buffer, since `opened_at` is stamped a few seconds after the triggering message — through `resolved_at` or now if still pending) get prefixed `_ESCALATION_MARKER` (`[handover follow-up]`) and the prompt is told not to let them lower the score. Live-tested head-to-head on a real stuck lead (marker present vs absent) — the marker applies correctly but didn't move the score in that specific case, so treat this as a plausible mitigation, not a proven fix, until it's observed changing a real outcome.
- **Score History was permanently empty for every lead until 2026-07-29 — silent `KeyError`, not a data problem.** `record_stage_event()`'s metadata build in `ai_reply.py` referenced a `"decay"` key that `compute_score()` stopped returning on 2026-07-26 (see that entry below); the resulting `KeyError` was swallowed by a broad `except Exception`, so `lead_stage_events` never got a `score_updated`/`segment_changed` row even though `leads.score`/`segment` updated correctly. Same bug also skipped `maybe_assign_lead()` (score-triggered auto-assignment) on every scored reply, main path only. Fixed by deleting the two dead `"decay"` references — if Score History is empty again in the future, suspect a *new* stale-key regression in that metadata dict before assuming it's a data/query issue.
- **No time-based decay (removed 2026-07-26, explicit user decision).** There used to be a bidirectional `decay` term (−4 stale over 30d+ ... +3 for replying within 1h) plus a 6-hourly `apply_engagement_decay_all` scheduler job that could silently move a lead's segment purely from the clock, with zero new message. Both are gone — `_compute_decay()`, the scheduler job, and `score_engagement_delta` writes are all deleted. A lead's score/segment now **only** changes when they send a new message; going silent has zero effect, in either direction. See decisions/log.md 2026-07-26.
- **The segment-A/assigned gate is GONE (2026-06-01).** Scoring fires on every inbound unconditionally.
- **Correction (2026-07-26): the "Per-broadcast scoring" claim below is stale — verify before relying on it.** `broadcast_lead_scores` (migration 076, `UNIQUE(broadcast_id, lead_id)`) is still real and still **seeded** score=5/seg=C at send time (`broadcast_executor.py`, `upload.py`). But `compute_score()` as it exists today takes **no `broadcast_context` parameter** and does not write to `broadcast_lead_scores` or `lead_tag_interest` at all — confirmed by reading the live function signature and grepping both files for writers. Whatever currently keeps a per-broadcast row's score in sync after a reply (if anything still does) was not traced this session — don't assume the old rollup-on-reply description is still accurate. Needs a fresh investigation; see active-backlog.md.
- `lead_scorer.py` (legacy two-pass) was deleted 2026-09-24 (`f779b16c`) along with `call_coach.py` / `call_digest.py`.

## Reply prompt: handover line, opt-out, reply eval (2026-09-24)
- **One HANDOVER RULE decides "I can't help / a human was asked for".** `_handover_rule_block()` in `ai_reply.py` reads the client's `handover_line` setting (Knowledge page, "When Aira can't help"). The knowledge header, missing-link rule, campaign block and escalation block all point at it instead of hardcoding "a team member will contact you". Empty line = old default wording. **Why:** Astro Tamil forbids promising contact; 52 live replies promised it anyway, mostly from the escalation block — in the reply eval, escalated leads went 0/3 → 3/3 once the client line was used.
- **A clear refusal now sets `opted_out`.** `compute_score()`'s rejection path writes `opted_out`/`opted_out_at` along with segment D. Before, only the exact words "stop"/"unsubscribe" (`webhook._is_opt_out`) opted a lead out, so 7 of Astro Tamil's 11 Not-Interested leads kept getting silence nudges after the AI told them they wouldn't be contacted. The AI still answers if the lead writes again; reactivate by hand via the upload.py endpoint.
- **Jina is limited to 2 concurrent requests per key** — `embeddings._post_with_retry` queues locally and retries 429s; before, 3 simultaneous leads silently dropped retrieval into the full-text fallback, which is now capped at `_FALLBACK_MAX_CHARS` (12k).
- **Reply eval: `backend/evals/replies/run_eval.py`.** Builds replies with the real `build_reply_system_prompt` + `_llm_chat` (DB stubbed), grades with fixed checks + a strict Gemini judge (counts an invented "we don't have X" as invented). 5 synthetic domains committed; real Astro Tamil cases gitignored. `--master-file` tests a master prompt edit before publishing; `--real-handover-line` tests a client line without saving it. 2026-09-24: 86% → 91% overall; remaining failures are mostly language mirroring (deliberately deferred).
- **Reply language is decided by the operator console setting (`reply_language_mode`), by design (operator, 2026-09-24).** The audience is Tamil Nadu, so the rules deliberately cover Tamil script, Tanglish and English only. Do not "generalise" mirroring to Hindi/Telugu/etc.; the reply eval grades language against the setting on that basis.
- **The master prompt is domain-neutral (published 2026-09-24).** Business-specific rules live in each tenant's profile, never in the master prompt — that is what lets one master serve astrology, real estate, clinics, etc. Before publishing a master change that REMOVES a rule, check which tenants relied on it (Astro Tamil, Astro Tamil - Co and Astrotamil Pooja had their astrology rules moved into their profiles first). Reply eval: old setup 67/71 vs new 66/71; other domains 36/39 vs 37/39.
- **Business profile = the description written under 6 fixed headings** (`services/business_profile.py`: about, how_to_buy, who, voice, job, never; per-section word guides, 700-word hard cap on PUT). Still stored as `business_description` text, so every reader works unchanged. `propose_conversion()` uses the tenant's reply model and **misjudges some lines as "already in the platform rules"** (seen live) — every conversion needs a human read of its "removed" list before saving.

## Call evaluation — TeleCMI v4 / CallIQ Steps 1-2 (2026-09-25/26)
- Pipeline, in order: `call_tracks` (splits the stereo recording) → `call_transcribe` (each track transcribed **separately**, then merged into one timed transcript) → `call_metrics` (talk share, interruptions, caps) → `call_quotes` (word-level quote validation) → `call_sorting` (Step 1: decides the call group) → `call_marking` (Step 2: the 10 checks + CRM update) → `call_scorer` (finalizes `score`/`score_status`) → `call_alerts` (warnings) → `scoring_rules` (shared constants: level marks, caps, cutoffs).
- **Stereo channel mapping is load-bearing, not assumed**: right channel = telecaller. Verified 2026-09-25 on live call `ed296fa2`, where a single merged-audio AI transcription pass had swapped the two speakers — this is exactly why each track is now transcribed on its own instead of one pass over the mixed audio.
- Calls under 30s are never transcribed or scored at all.
- **Step 1 (grouping) is arithmetic, not AI**: the system counts quote-validated signs and picks `not_connected` / `very_short` / `early_exit` / `real_conversation` itself — the AI never chooses the group.
- **Quote matching is word-level** (`call_quotes.find_quote`): exact match required for words under 4 characters; longer words tolerate a `SequenceMatcher` ratio ≥0.8. A pure character-ratio matcher was tried first and accepted negation-flipped quotes ("no extra charge" vs "an extra charge" scored 0.89) — replaced for that reason (see decisions/log.md 2026-09-26, R7).
- **Step 2**: the AI picks a level (good/poor/etc.) per check only; the system computes every mark from `scoring_rules` constants. Check 10 (CRM update) is left pending until the wrap-up is saved, then AI-compared against it; Missing if no wrap-up within 2 hours (`crm-cutoff-sweep` scheduler job, every 10 min).
- Warnings go to `call_alerts`: the admin-only **Needs attention** list + sidebar badge, one **09:00 IST** summary notification, and instant alerts only for `rude`/`wrong_info`, capped at 1 per telecaller per hour. Quotes on alerts and checks are sent to the browser (clipped); the full transcript stays masked (first/last line only) same as before.
- `MAX_ATTEMPTS = 2` retries per call before giving up. **SIM calls (`sim_basic` provider) are never scored** — test/demo traffic only.
- `call_logs.score_status` check constraint still allows the old pre-v4 values (`pending`/`awaiting_outcome`/`short_call`/`no_answer`/`no_recording`/`scored`) alongside the new set until migration 207 runs post-deploy and narrows it (see decisions/log.md).
- Gone in this rebuild, don't look for them: `call_summarizer.py`, `call_digest.py`'s old composite, and the `0.5×outcome + 0.5×AI` score blend — scores are now a straight 100-point sum of the 10 checks.

## AI provider keys & billing model (all providers, 2026-07-17)
- **Every provider is strictly per-tenant, zero platform fallback** — Sarvam, Gemini, OpenAI, Groq, Jina. `require_tenant_setting(key, tenant_id)` raises if the tenant hasn't configured it; there is no silent drop to a platform/env-var key anywhere in the AI call paths. This is deliberate: **the operator (not the client) pastes each tenant's own keys into the operator console** so each provider's own dashboard shows accurate per-client cost/token usage — a platform fallback would silently defeat that and hide real cost exposure. Don't reintroduce an `x or settings.y_api_key`-shaped fallback in any new AI code path; it undoes the whole point.
- **`ai_reply_model` itself now has zero silent fallback too (2026-07-18)** — previously fell back to a hardcoded `_DEFAULT_REPLY_MODEL = "sarvam-30b"` constant when a tenant hadn't explicitly configured one. (The removal was originally justified by a "sarvam-30b is deprecated" claim that the operator later corrected as **wrong** — sarvam-30b is live. The decision stands on its own rationale anyway: Sarvam is one of four equal reply providers — Sarvam/Groq/Gemini/OpenAI — each selected per tenant by the operator, so no provider deserves a hardcoded default.) `_resolve_reply_model()` now calls `require_tenant_setting("ai_reply_model", tenant_id)`, same contract as every provider API key — an unconfigured tenant gets no AI replies at all (fails into the existing log-and-skip handler at `webhook.py`'s `generate_reply` call site). The operator console's model picker (`config.tsx`) also stopped labeling Sarvam 30B as "Default. Best fit..." — it's still selectable, presented as a peer of the other providers rather than the recommended choice. Don't reintroduce a `_DEFAULT_REPLY_MODEL`-shaped constant.
- **Only exception: `meta_app_secret`.** Stays platform-critical, but structurally, not as a billing choice — there's one shared Meta Developer App behind every tenant's WhatsApp Embedded Signup, so there's nothing to make per-tenant. (It IS still stored per-tenant in `app_settings` for `verify_meta_signature`'s uniform lookup, auto-copied from the platform value during Embedded Signup — that's a lookup-convenience detail, not a second Meta app per client.)
- **Jina bridge key (temporary, 2026-07-17):** the 2 tenants that existed when Jina went tenant-strict were bootstrapped onto one shared key so RAG/catalog search didn't break on deploy. Replace each with its own distinct Jina key when convenient — sharing one key means Jina cost still isn't separated per client, defeating the point.
- **GPT-5 family reasoning params are generation-specific and mutually exclusive** (`openai_client.py`): needs `max_completion_tokens` not `max_tokens`, and rejects non-default `temperature`. `reasoning_effort` must be `"minimal"` for the original gpt-5/gpt-5-mini/gpt-5-nano family (`"none"` 400s there) but `"none"` for dotted point releases like gpt-5.1/gpt-5.4 (`"minimal"` 400s there instead) — branch on `model.startswith("gpt-5.")`. Get this wrong and gpt-5-nano doesn't error, it silently burns its whole token budget on hidden reasoning and returns an empty string.
- **Gemini 3.x chat models default to `thinking_level: "medium"`** (`gemini_client.py`'s `generation_config`) — on `gemini-3.5-flash` this ate most of a 300-token reply budget on the hidden thought step, live-tested to either 30s-timeout or return text truncated mid-sentence. Set to `"minimal"` on both `gemini_chat_completion`/`gemini_chat_completion_with_tools`. `gemini-3.1-flash-lite` shares the same default but is fast enough it doesn't visibly show the problem — don't assume it's exempt if you change token budgets later.
- **`gemini-2.5-flash-preview-tts` is the current `DEFAULT_GEMINI_TTS_MODEL` (2026-07-17, reverted for cost — ~half the price of `gemini-3.1-flash-tts-preview`).** It hard-400'd ("Model tried to generate text, but it should only be used for TTS") earlier the same day, then worked again later with no code change — a preview-model flake on Google's side, not fixed by anything in this repo. Operator explicitly accepted the risk it could flake or get deprecated again with no warning; if it's next observed broken, swap back to `gemini-3.1-flash-tts-preview`. Don't assume today's working state is permanent.
- **`gemini-2.5-flash` shuts down 2026-10-16** (Google's own deprecation page, `gemini-3.5-flash` listed as replacement) — ruled out as the call-analysis model for this reason during the 2026-07-18 migration despite being otherwise well-suited; don't pick it for new work without rechecking that date first.
- **Gemini's `/v1beta/interactions` endpoint accepts audio/image/document input via a flat content-part shape** (live-tested 2026-07-18): `{"type": "audio"|"image"|"document", "data": <base64>, "mime_type": ...}` as a sibling to `{"type": "text", "text": ...}` in the `content` array — NOT the standard Gemini API's nested `inline_data` convention this endpoint otherwise superficially resembles. `"document"` (not `"file"`) is the type for PDFs; both `image` and `document` types were confirmed with real OCR output (exact verbatim text extraction), and `audio` was confirmed with a real transcription attempt. Used in `gemini_speech_to_text()`/`gemini_extract_document_text()` (`gemini_client.py`).
- **Gemini's formal JSON-schema response mode is broken on this endpoint** (live-tested 2026-07-18): `response_format: {"type": "object", "schema": {...}}` is accepted by request validation (the `type` enum is `object`/`string`/`array`/`boolean`/`text`/`image`/`audio`/`video`/`integer`/`number` — NOT `"json_object"`/`"json_schema"`, a different convention than OpenAI/Groq), but the model emits `{` followed by unbounded whitespace and never completes, regardless of `max_output_tokens` (tried up to 800). `gemini_chat_completion_json()` uses prompt-only "return JSON only" instead (same discipline `gemini_chat_completion` already relies on for plain replies), plus one retry on a parse failure since there's no hard guarantee here unlike Groq's `response_format={"type":"json_object"}`. Don't retry the schema mode without live-retesting first — it may get fixed on Google's end, but wasn't as of this test.
- **`maybe_single().execute()` returns `None` outright** (not an object with `.data=None`) on zero matching rows in this supabase-py version — guard `if x and x.data`, not just `if x.data`. `operator.py`'s `client_overview` hit this for a tenant with no `tenant_users` owner row (fixed 2026-07-17, see decisions/log.md); **still not swept across the other 20+ `maybe_single()` call sites in `operator.py`** (see active-backlog.md).

## Frontend performance pattern
- **Recipe:** `page.tsx` (async server component) fetches a seed via `lib/serverApi.ts serverFetchJson<T>(path, token, 2500ms)` (timeout-guarded → null on fail; MANDATORY or a cold backend white-screens SSR) → passes to a `<Route>Client.tsx` as SWR `fallbackData`. **Gate on DATA presence, not role** (seeded owners skip the spinner).
- `lib/api.ts apiFetch`: GET-only retry (network/timeout/502-503-504) + backoff + 30s GET timeout. **Mutations NEVER retry** (no double broadcasts/sends/assignments).
- Server components: `import type` for `@/lib/api` types (it pulls the browser supabase client).
- Backend runs on Render **Starter** (no idle sleep), but the process still restarts ~every 5h — see "Deployment (Render)" above for what that does to APScheduler interval jobs. The 14-min keep-alive cron dates from the free tier (which slept after 15min and skipped scheduler jobs) and is now redundant. One scaling caveat: externalize APScheduler before running >1 backend instance.

Diagnose by reading the overlay's `getBoundingClientRect()` and computed `margin-top`, not its `z-index`. The fix on the knowledge page was to drop `space-y-6` from the page root: both tab branches already carried their own, and the wrapper's only other children were fixed overlays that do not participate in flow layout, so it spaced nothing and existed purely to cause this. ## Frontend styling conventions (Tailwind + `.input` utility)
- **`globals.css`'s `.input` class (padding/border-radius/focus-ring) and a Tailwind padding utility (`pl-9` etc.) on the same element are both single-class-specificity — which one wins is cascade-order-dependent, not guaranteed.** The existing convention in this codebase (e.g. `templates/page.tsx` search box) is to override `.input`'s padding via an inline `style={{ paddingLeft: ... }}` instead of a `pl-*`/`pr-*` Tailwind class, since inline style always wins regardless of stylesheet order. Follow this pattern rather than fighting the cascade with utility classes. Custom bordered controls that don't use `.input` at all (e.g. the select/dropdown wrappers on that same page) sidestep the issue entirely.
- **Brand color for interactive UI state is `primary` (violet, `#5b21b6`)**, not `emerald`/`green` — emerald is reserved for "Approved"/status-positive semantics elsewhere (template status badges, stat tiles). Active toggle/tab states in a control bar should use `text-primary`/`bg-primary`-family classes, not emerald, to stay visually consistent with what emerald already means in this app.

- **`animate-in` / `fade-in` / `zoom-in-*` / `slide-in-from-*` are DEAD CLASSES in this repo — they emit no CSS (found 2026-09-05).** They are `tailwindcss-animate` utilities, and that plugin is not a dependency (`frontend/package.json` has no `animate` entry, `node_modules/tailwindcss-animate` does not exist, `tailwind.config.ts` has `plugins: []`). 26 usages across 10 files currently render with no animation at all, silently — Tailwind does not warn about a class it can't generate, and the element still looks correct, just static. **Verify by grepping the built CSS, not the source**: `npm run build && grep -c animate-in .next/static/css/*.css` returns 0. For a new animation, add a keyframe + a single `.animate-*` class to `app/globals.css` (the existing `.animate-slide-up` and the `popover-in` added 2026-09-05 are the pattern; both carry a `prefers-reduced-motion` opt-out) rather than reaching for the plugin's class names.

### SIM call tracking — Android "Aira Sync" APK (`android/`, 2026-07-02)
- Companion native app, NOT part of the PWA/Next.js build. Purely a background sync daemon — no CRM UI, no dialer of its own. Reads `CallLog.Calls` via `ContentObserver` (near-real-time) + a 30-min `WorkManager` periodic fallback, filters to numbers matching the caller's assigned leads (`GET /calls/sim-lead-numbers`), and POSTs matches to `POST /calls/sim-cdr` with `X-Sync-Token` auth. `callers.sync_token` (migration 122) is the per-caller secret, minted via `POST /callers/{id}/sync-token` (owner-only).
- **Fail-closed privacy filter**: if the lead-numbers fetch fails, `SyncWorker.kt` returns `Result.retry()` and uploads nothing that round. Personal calls are never even attempted for upload — the filter runs before any network call to `/sim-cdr`.
- **Foreground service permission ordering is load-bearing**: `SyncService.onCreate()` MUST call `startForeground()` unconditionally first (Android kills a service that doesn't enter foreground promptly), THEN check `READ_CALL_LOG` and `stopSelf()` if missing. Registering the `CallLog.Calls` `ContentObserver` before checking the permission throws an unhandled `SecurityException` and crashes the whole app on first launch — this was a real shipped bug, fixed 2026-07-02. `AiraSyncApplication.onCreate()`/`BootReceiver` must also gate `SyncService.start()` behind a permission check, or the service (and its crash) fires on every app relaunch/reboot before setup is complete.
- **Distribution is live (2026-08-07)**: not on Play Store (`READ_CALL_LOG` is Play-restricted to default-dialer apps), sideload-only. Signed release APK hosted at the public Supabase Storage bucket `app-releases` (`aira-sync.apk`, migration `169`) — same URL every release, re-upload with `upsert: true` to ship an update. Signing key is `android/keystore/aira-sync-release.jks` + `android/keystore.properties` (both gitignored, PKCS12 so store/key password must be identical — keytool silently ignores a distinct `-keypass`). **This keystore is the app's permanent identity — if it's lost, every future update requires every device to uninstall/reinstall.** Download link + per-telecaller sync-token minting UI live on the client dashboard's Roles page (owner-only, gated on `callingProvider === "sim_basic"`) — deliberately NOT exposed to the telecaller's own view, same precedent as temp-password issuance (owner mints, relays out-of-band during phone setup).
- **Build-artifact trap (hit 2026-08-07)**: a build's file mtime is not proof it matches current source. The only APK that existed pre-2026-08-07 was built one minute after the Phase 2 recording-upload commit, two days *before* that feature was reverted — nobody had rebuilt it since, so it still shipped the abandoned Recordings UI calling a backend route that no longer existed. Before trusting an installed/built APK reflects `main`, check its build timestamp against the relevant commit dates (`git log -- android/`), especially after any revert.
- Double-count risk: unreconciled with the PWA cockpit's own `sim_started` row creation (see `sim-dialer.ts`/`useCallingCockpit.ts` above) — if a telecaller dials via both paths for the same call, two rows can result. See active-backlog.md.
- **Enrichment reconciliation is order-independent (fixed 2026-07-03)**: the lookup in `_ingest_sim_call` that matches a fresh APK sync to an existing PWA-created row is gated ONLY by `call_sid IS NULL` (not by `status IN (sim_started, initiated)`) — so it doesn't matter whether the wrap-up form or the APK sync completes first, they always converge on one row. The `updates` dict the APK path writes must stay hard-facts-only (`call_sid`/`status`/`disposition`/`duration_seconds`, outcome only if the human hasn't already tagged one) — never `notes`/`tags`/`quality_rating`/`manual_started_at`/`manual_ended_at`, which stay human-owned regardless of ordering.
- **Recording upload (Phase 2) was built, then reverted 2026-07-05** — see decisions/log.md for the full writeup. Root blocker: whether a phone auto-records calls at all depends entirely on which app is set as the **default dialer**. Google's Phone app (common default even on non-Pixel phones) gates recording behind a manual per-number whitelist (Play policy, region-gated) — it does NOT blanket-auto-record. OEM native dialers (MIUI's stock Dialer, etc.) DO auto-record unrestricted, because they're privileged system apps — this is also why the known-path folder list (`/storage/emulated/0/MIUI/sound_recorder/call_rec` etc.) only ever gets populated when the OEM's own dialer is active, not Google's. Building an in-app recorder instead isn't a viable workaround: Android has restricted the `VOICE_CALL`/`VOICE_UPLINK`/`VOICE_DOWNLINK` audio sources to privileged/system apps only since roughly Android 9/10, which is exactly why standalone recorder apps work on Xiaomi/MIUI but not stock Android/Pixel. Any future revival of this feature needs a per-telecaller onboarding check (confirm default dialer + its native recorder's auto-record setting) before assuming recordings will exist to harvest — Phase 1 (call-log metadata only) does not depend on any of this and is unaffected.

- **`_latest_sim_app_version` cache: "never fetched" must not look fresh (2026-10-03).** The cache started at `at=0.0` and checked `monotonic() - at < TTL` (600 s). On Linux `time.monotonic()` is uptime, so on a new CI runner or a just-restarted Render container it is under 600 and the never-filled cache counted as fresh: the version came back `None` without a fetch for the first 10 minutes. Fixed by treating `at == 0` as unfetched. Any monotonic-based cache in this codebase has the same trap.

## Channel settings save path (app_settings.py PATCH /api/v1/settings/)
- **Save handlers for every channel (WhatsApp/Instagram/Facebook/Telegram) MUST be DB-write-only — no outbound HTTP calls.** WhatsApp/IG/FB saves always were (upsert credentials, set `{channel}_status="configured"`, return in milliseconds). Telegram's save handler was the one exception: it called `setup_telegram_webhook()` synchronously inside the PATCH request, making a live outbound call to `api.telegram.org/bot{token}/setWebhook` before responding. On Render's free tier this occasionally hung/timed out long enough that the proxy killed the connection before any HTTP response reached the browser — the frontend's `fetch()` never got a response at all (native rejection, not an HTTP error), so it fell back to a generic "Cannot reach the server" message. **Fixed 2026-07-02** by moving `setup_telegram_webhook()` out of save entirely; save now only validates the token format (`\d+:[A-Za-z0-9_-]+` regex) and persists `telegram_status="configured"`, matching the other three channels exactly. The outbound `setWebhook` call now only happens in `POST /activate` (user-initiated "Validate & Activate" button click), where a slow/failed Telegram API call is an expected, bounded, user-visible wait — not a silent request killer.
- **Diagnostic trap**: a `net::ERR_FAILED` / "Cannot reach the server" browser error with NO HTTP status code (not 400/502/504) means the TCP connection died before any response — this is NOT a CORS rejection even if the browser's console prints a CORS-looking message (Chromium shows generic CORS text for any cross-origin connection failure since it has no response headers to inspect). Rule out CORS by checking whether *other* channels' saves succeed from the same origin/session — if WhatsApp/IG/FB save fine but Telegram doesn't, the failure is channel-specific code, not CORS config. This exact confusion cost several debugging rounds before the user pointed out the differential symptom.
- **`get_setting()` (`config_dynamic.py`) previously conflated "not configured" with "DB read failed."** A transient Supabase disconnect (httpx `Server disconnected`, a dropped pooled keep-alive connection) during a `get_setting` call was silently swallowed and returned `None` — indistinguishable from a genuinely-unset credential — and that `None` got cached for `_TTL` (60s), so `_creds()` in `meta_cloud.py` would raise "Meta credentials not configured. Set them in Settings." (and fire the owner's `system_error` notification) even when `app_settings` had valid, current credentials. **Fixed 2026-08-07**: `get_setting` now retries once immediately on any read exception (clears most transient blips before they're ever visible to the caller) and only writes to `_CACHE` on a confirmed read — a failed read is never cached, so the next call re-hits the DB instead of serving a false negative for the rest of the TTL window. Diagnosed by cross-referencing the `app_notifications` row's timestamp against Render logs for that exact second — the `get_setting(...) DB read failed: Server disconnected` warning was right next to the misleading error.

## Web Push
- Web Push is permission-gated from the notification bell and stored in `push_subscriptions`. Backend delivery is best-effort via VAPID keys and must not block assignments if a subscription is stale or push config is missing.
- `GET /api/v1/push/public-key` is intentionally public (`push.public_router`); it returns only the VAPID public key. Subscription save/delete/status routes stay auth-gated. Frontend `syncPushSubscription()` must no-op when there is no Supabase session so anonymous pages do not spam 401s or redirect back to `/login`.
- **Push is gated by `notification_config` at ONE chokepoint** (added 2026-07-01): `notify_user` calls `notification_config.push_allowed(tenant_id, type)` and skips ONLY `send_user_push` (the in-app `app_notifications` row is ALWAYS written) when the master switch is off, the per-event toggle is off, or the current IST time is inside quiet hours. `push_allowed` is **fail-open** (config read error → allow) so a config hiccup never silently drops pushes. To add a new push event, give it a key in `_NOTIFICATION_CONFIG_DEFAULT["events"]` and the panel/whitelist; unknown types default to allowed.

## Callback notifications (services/callback_notifications.py — claimable-only)
- **1-min job `callback-notifications`** replaced the old `callback-reassignment` auto-move (2026-07-01). Two passes: (1) DUE — `scheduled_for <= now` & `due_notified_at IS NULL` → push `callback_due` to the lead's **assigned** caller; (2) CLAIMABLE — `scheduled_for <= now - threshold` & `claimable_notified_at IS NULL` → `notify_callback_claimable` to the configured audience, **with NO shift/availability check** (out-of-shift owners included). Guard columns are set on fire (once-only); `reschedule_callback` nulls both to re-arm. **There is NO auto-reassignment** — overdue callbacks are pulled manually via `POST /leads/{id}/takeover` (still CAS-guarded), which now also pushes the previous owner (`callback_taken_over`).
- **Threshold + audience are config:** `notification_config.claimable_threshold_minutes` (default 15); `claimable_audience` ∈ `telecallers_and_admin | telecallers_only | admin_only | specific` ("specific" uses `claimable_caller_ids`, owner NOT auto-added). Claimable recipients = enrolled callers (`active=True`, **ANY status** — push must reach app-installed-but-logged-out callers via their `push_subscriptions` row) + owner, minus the current owner.
- **Gotcha:** the migration-122 guard columns (`due_notified_at`/`claimable_notified_at`) MUST exist before the job runs, or the `.is_(...,"null")` filters error every tick (caught per-tenant, logged, no-op). v1 limitation: push `tag` falls back to the bare type (no `dedupe_lead_id`), so simultaneous same-type pushes can collapse on the device lock screen — the in-app bell keeps all.

### Operator Console — Itemized Subscriptions (2026-07-04, client-driven cart — supersedes the 2026-07-02 admin-assigns-one-plan model above)
- **The model changed from "admin assigns a tenant one plan" to "tenant builds their own itemized cart, admin approves it."** `tenant_subscriptions.plan_id` still exists but is now just a display-only "started from this package" pointer — **never authoritative for entitlements**. The source of truth is `tenant_subscription_items(tenant_id, feature_key, quantity, unit_price_snapshot)`, one row per purchased feature_key. `resolve_entitlements(db, tenant_id)` keeps the exact same signature/return shape (`{"features": [...], "quotas": {...}}`) but now reads `tenant_subscription_items` joined against `feature_catalog.depends_on`/`usage_metric`/`included_qty`, not `plans.feature_keys`/`quotas`. `get_purchased_quantity(db, tenant_id, feature_key)` is new — sums quantity for one feature_key, used by hard-cap checks.
- **`feature_catalog.depends_on`** (existed since migration 123, never wired up until now) is what turns a purchased SKU into a bundle of internal flags: e.g. buying `outbound_messaging` also enables `whatsapp`/`broadcast`/`templates`/`auto_reply`/`human_handover`. The 8 client-facing sellable SKUs are `inbound_messaging`, `outbound_messaging`, `telecalling_sim`, `telecalling_telecmi`, `bulk_lead_upload`, `telecaller_seats`, `numbers_pool`, `notifications` — everything else in the 43-row catalog is an internal flag, never priced/purchased directly.
- **`check_quota()` is no longer dead code and no longer upserts.** It's now a pure read: `True` iff `used + delta <= included` for the current period, `False` (blocked) if there's no counter row or `included == 0` — this INVERTS the old dead-code behavior where `included == 0` meant "unlimited." Callers must call `check_quota()` **before** attempting the action and `meter()`/`increment_usage()` **after** it succeeds — they're two separate steps now, not one. Wired into 4 places: `team.py::invite_member` (against `get_purchased_quantity(..., "telecaller_seats")`, a live COUNT comparison, not a period counter), `numbers.py::create_phone_number` (same pattern against `numbers_pool`), `ai_reply.py::generate_reply` (against `ai_reply` metric, fails safe — returns early like the existing blocked-lead branch, webhook callers still get their normal 200), `calls.py::initiate_call` (against `call_minute`, checked at initiation since minutes are only known after a call ends via the TeleCMI CDR webhook). **`broadcast_executor.py` is deliberately NOT gated** — outbound message sends stay track-only `meter()`, by explicit user scope decision mid-build.
- **Package price is always computed, never hand-typed.** `plans.discount_percent` (new column) + `plans.feature_keys` (same column, repurposed: now `[{feature_key, quantity}]` instead of a flat key list) feed `_compute_package_price()` in `operator.py`, which resolves each item's price as `unit_price if not null else monthly_price` (mirrors `subscription_requests.py::_price_for_item`) — **do not just read `monthly_price`**, `telecaller_seats`/`numbers_pool` have `monthly_price=0` and are priced entirely via `unit_price × quantity`.
- **Feature Store is gone entirely** (not just repurposed this time) — `client/[id]/views/feature-store.tsx` deleted, replaced by a read-only `entitlements.tsx` (current `tenant_subscription_items` + `tenant_subscriptions.status`, no plan-assignment action of any kind). The old `GET/PATCH /clients/{tenant_id}/subscription` plan-assignment routes are deleted from `operator.py`. Assigning entitlements to a tenant now only happens by approving a `subscription_requests` row (`POST-adjacent` `PATCH /operator/subscription-requests/{id}`), never by a direct admin action on the tenant.
- **New tenants start with NO `tenant_subscriptions` row at all** (gated — the frontend shell treats a missing row as `status: "none"`). `create_client` no longer creates one, no longer seeds `enabled_features`/`tenant_usage_counters` from a plan. Existing tenants (created before this shipped) were backfilled to `status='active'` via `insert ... on conflict (tenant_id) do nothing` — **this only works if the tenant genuinely has no row yet**; if a tenant already has a row at some other status (e.g. `trial`, from the ordinary pre-this-feature onboarding flow), the backfill silently no-ops for it and it must be reconciled by hand with a tenant_id-scoped `UPDATE`, never a broad status-based one (risks clobbering deliberately `suspended`/`past_due` tenants).
- **`ClientLayout.tsx` gates the ENTIRE dashboard** on `GET /api/v1/subscriptions/me`'s `status` field — `"none"`/`"pending_approval"` renders only the full-page Subscriptions cart (no sidebar, no other route reachable regardless of URL), `"active"` renders normally. Fails open to `"active"` on any fetch error (network blip, cold start) — a broken subscriptions endpoint must never lock out an already-approved tenant.
- **Sidebar Toggle and Calling Provider Sync (Migration 129)**: Approving a subscription request or calling `sync_client_toggles(db, tenant_id)` recomputes entitlements and synchronizes client console toggles (`enabled_features` in `tenants`) and `calling_provider` in `telecalling_config`. Old billing-derived keys are automatically removed to mirror the active subscription items, while non-billing-derived keys (e.g. `analytics`) survive untouched. Standalone `notifications` is bundled directly into `inbound_messaging` and `outbound_messaging`. Testing this requires passing `db` to `get_telecalling_config` and `save_telecalling_config` (which now accept an optional `db` parameter to prevent unit tests from triggering live Supabase connections via `get_supabase()`).

## WhatsApp templates & admin notifications (2026-07-03)
- **`notification_config.py`'s merge is hand-rolled per-key, not a generic deep merge.** `get_notification_config` explicitly special-cases `events`/`quiet_hours`/`whatsapp_notifications` by name and whitelists specific scalar keys from the stored row. A new nested config key will NOT survive automatically — it must be added to `_NOTIFICATION_CONFIG_DEFAULT`, the merge block in `get_notification_config`, AND `NotificationConfigIn`'s Pydantic schema + `update_config`'s explicit persistence dict, or it's silently dropped (Pydantic ignores unknown fields by default; the PUT handler only writes keys it explicitly lists).
- **`growth.py::record_stage_event` is a plain sync function with no `BackgroundTasks` access**, called inline from ~9 request-path call sites (`leads.py`, `calls.py`, `facebook.py`, `instagram.py`, `telegram.py`, `upload.py`, `webhook.py`, `ai_reply.py`) — several run inside the user-facing `PATCH /leads/{id}` request. No Celery in this codebase. Fire-and-forget pattern used: `asyncio.get_running_loop().create_task(...)` guarded by `try/except RuntimeError` (no-op + log if no loop), with the task held in a module-level `set()` (`task.add_done_callback(set.discard)`) — otherwise it can be garbage-collected mid-flight, a well-known asyncio gotcha.
- **For single/low-volume `send_template_message` calls, pass only `tenant_id`** (not `phone_number_id`/`access_token`) — `meta_cloud._creds()` resolves the tenant's primary WhatsApp number internally. This is the pattern `reengagement_service.py::_send_step_template` already uses. Only bulk broadcast senders (`broadcast_executor.py`, `upload.py`) need the heavier `outbound_router.get_best_number`/`increment_send_count` pair for per-number rate/quality tracking — don't reach for that pair on a low-volume alert path.
- **`process_due_reengagements` must stay batched (fixed 2026-08-06, was N+1)** — it runs every 1 minute via the `reengagement-rules` APScheduler job, across every tenant/lead. A per-lead `reengagement_logs` existence check (and, on the broadcast branch, a per-lead `leads` fetch) was firing one Supabase round-trip per lead per tick — 100 sequential calls in 10s observed in Render logs — which saturated the Starter instance's 0.5 CPU every tick and starved the `/health` check into repeated Render flap (instance-failed/recovered) even though the plan had zero free-tier sleep involved. Use `_already_processed_lead_ids()`/`_fetch_leads_by_id()` (batched `.in_()` lookups) and keep delay/segment/source filtering in-memory *before* any DB call — don't reintroduce a per-lead loop here. See decisions/log.md 2026-08-06 entry.
- **`message_templates` has a `UNIQUE(tenant_id, name)` constraint checked in app code before Meta is ever called** (`templates.py::create_template`, line ~91). A POST with a name that already exists locally 409s regardless of that row's `status` — including a row that failed at Meta and never got a real `meta_template_id`. Repair path is PATCH (only allowed when `status` is `REJECTED`/`PAUSED`) or DELETE+recreate, never a second POST with the same name.
- **`whatsapp_notifications.recipient_phones` must never overlap with a real/test lead's own phone number in the same tenant (learned 2026-07-06)** — the admin segment-change alert sends to every number in `recipient_phones` whenever ANY lead crosses into a `target_segments` value, with the LEAD's name filled into the template. If an admin/tester's own number is both the recipient AND a tracked lead, they'll receive alerts about *other* leads' (or their own) segment changes on the same WhatsApp thread they use for customer-side testing — reads exactly like a broken duplicate-auto-reply bug but is pure config. Also confirm `template_id` actually points at internal-facing admin copy ("Lead {{1}} just moved to {{2}}") — `aira_connect` (the default in at least one tenant) is a customer-facing "thanks for reaching out" template and produces nonsensical copy when used for this alert.
- **Nothing writes `submitted_at`/`approved_at` unless you say so — the DB default only fires on INSERT.** `create_template` reuses a same-name row from a previous WABA via UPDATE (`stale_existing_id`), and `PATCH /templates/{id}` resubmits an edited one; both must explicitly reset `submitted_at`/`approved_at`/`rejection_reason` or a brand-new PENDING template displays the *previous* submission's dates. This shipped broken and was only caught by a user noticing a July "created" date on a template submitted minutes earlier (fixed 2026-08-15).
- **Meta returns the literal string `"NONE"` for `rejected_reason` on templates that were never rejected.** `if meta_info.get("rejected_reason")` is truthy for it, so all three ingest paths used to store `"NONE"` verbatim and the detail page rendered a red "Template Rejection Detail: NONE" banner on healthy templates. Normalise through `_clean_rejection_reason()`.
- **`approved_at` is not "when Meta approved" unless you guard it.** Sync stamped `now()` on every run, so the approval date silently drifted to the last sync — four unrelated live templates all ended up sharing one batch timestamp. Only stamp when the row has no `approved_at`, and clear it when Meta reports a non-approved status. Meta's API returns no approval timestamp, so a drifted date is **unrecoverable**.
- **Meta template hard rules learned from live rejections** (Graph API `error_subcode`): `2388299` = a `{{n}}` variable can't be the first or last token of the body — trailing punctuation right after the last variable (e.g. `{{4}}.`) is NOT sufficient, Meta wants real trailing text/words. `2388293` = "words ratio" limit on variable count vs. body length — formula is undocumented; treat as a soft heuristic (roughly 6+ words per variable), not a hard rule. Positional `{{n}}` must be numbered sequentially from 1 with no gaps. All three are now validated both client-side (`frontend/app/dashboard/templates/types.ts::validateTemplateBody`/`templateBodyWarning`) and server-side (`templates.py` Pydantic validators on `CreateTemplate`/`UpdateTemplate`) — the deterministic two are hard-blocked, the ratio one is a warning only.

## WhatsApp templates - WABA scope and CORS masking (2026-07-10, visibility reworked 2026-08-15)
- `message_templates.meta_waba_id` records which Meta WhatsApp Business Account a synced/created template belongs to. `GET /api/v1/templates/` filters rows to the active `app_settings.meta_waba_id`.
- **Two functions that look interchangeable and are not (`templates.py`).** `_filter_templates_for_waba` answers *visibility* and fails **closed** — no `meta_waba_id` configured returns `[]`, so a disconnected tenant sees an empty templates page. `_belongs_to_current_waba` answers *ownership* and fails **open** — no WABA configured returns `True` for every row, because it also backs the duplicate-name check in `create_template`; making it fail closed lets an unconnected tenant insert same-name rows. Don't "simplify" these into one function. Both have tests pinning the split.

Deleting rows to "clean up" after an account switch destroys it permanently. Hiding costs nothing and reconnecting the same WABA restores the list on the next page load.
- **Creating a template with no WABA connected 400s** (`Connect Meta WhatsApp (meta_waba_id) in Settings first`). Before 2026-08-15 it saved a local PENDING row that never reached Meta; with visibility failing closed that row would also be invisible, so the branch was removed. There is no "draft" concept in the product — every `message_templates` row is Meta-backed.
- **The operator console (`operator.py`, tenant detail) lists templates deliberately unfiltered** — support needs to see a disconnected tenant's rows. Don't apply `_filter_templates_for_waba` there.
- If a client switches Meta accounts and old approved templates still appear, first verify the live DB has `meta_waba_id` and that the app code writing/filtering it is deployed.
- `https://www.anrilaitech.com` (new) and `https://www.bloommatrix.in` (legacy) are both in `backend/app/main.py`'s CORS allowlist. If `/api/v1/templates/sync-from-meta` shows "No Access-Control-Allow-Origin" in Chrome, check Render/backend logs and schema drift first, especially missing columns such as `message_templates.meta_waba_id`; a server 500 can be masked by the browser as CORS.

## Ad attribution — Meta CTWA vs Google tag (webhook.py, 2026-07-05)
- **Two independent attribution mechanisms feed the same `leads.ad_campaign_id` + `ad_campaigns` table**, both in the WhatsApp webhook's inbound loop, Meta block first then Google:
  1. **Meta CTWA/referral** — `msg.get("referral")` with `source_type=="ad"`. ONLY Meta populates this (Click-to-WhatsApp, and the parallel FB/IG DM webhooks). Google/organic messages never have it.
  2. **Google tag** — `parse_google_ref(body)` looks for a `[GADS:<slug>]` tag in the message text, injected via a `wa.me?text=` pre-fill on the Google ad. This is the ONLY way Google traffic gets attributed — Google cannot send Meta's referral object.
- **Order + guard is load-bearing**: the CTWA block sets a local `ad_attributed` bool; the Google block runs `if not ad_attributed` AND only writes when `leads.ad_campaign_id` is currently null. So Meta always wins if both are somehow present, and a repeat tagged message never re-stamps or duplicates the campaign. Don't reorder these or drop the null-check — you'll double-count or let Google overwrite a Meta attribution.
- **Tag format lives in ONE file** (`services/google_ads_attribution.py`) used by BOTH the parser (webhook) and the link generator (`/inbound-leads/google-link` endpoint + UI modal). If you change the regex, the generator's `[GADS:...]` output must change with it — the `test_build_link_round_trips_through_parser` test is the tripwire. `external_campaign_id` is namespaced `google:<slug>` to avoid colliding with Meta numeric ad ids in `get_or_create_campaign`'s external-id lookup.
- **`gclid` is captured but inert** — parsed and logged, not yet resolved against the Google Ads API. Real Google spend / cost-per-lead is NOT populated (unlike Meta where `ad_campaigns.spend_inr` can be set). The comparison-table USP shows lead *counts* per platform today, not cost, until the gclid→Ads-API reconciliation is built.
- **Attribution depends on the client using the generated link.** A bare `wa.me` number with no tag → lead stays `organic`, Google uncredited. This is why the generator is a UI button (no hand-typing) — but it's still a client-onboarding dependency, not something the platform can enforce.

## Subscription billing addendum - flat modules, unlimited phase (2026-07-05)
- **Supersedes the earlier 2026-07-04 cap wording in this file.** During the current phase, `tenant_usage_counters.included` is informational only. `check_quota()` must return false only when an explicit `hard_cap` exists and the delta would exceed it. Missing rows, `included=0`, and old finite included values must not block AI replies, telecalling, messaging, seats, or phone numbers.
- **Flat-price modules**: `inbound_messaging`, `outbound_messaging`, `telecalling_sim`, `telecalling_telecmi`, and AI tier rows are subscription entitlements, not metered usage products. Treat `monthly_price` as the product price. Do not add per-message, per-call, or per-reply enforcement unless the product decision changes again.
- **Quantity concepts are not enforcement yet**: AI tokens may still be shown/tracked, but the AI-reply path should not hard-block on included counters while this unlimited phase stands. `hard_cap` remains the escape hatch for a deliberate client-specific stop. **Telecaller seats and numbers pool are the exception — see the 2026-07-31 addendum below, which supersedes this bullet for those two.**
- **Proration**: Add-on requests for existing tenants charge only the remaining fraction of their current anchored monthly billing cycle. For newcomers (initial requests), they specify custom start/end dates (defaulting to 15 days), and the backend calculates proration as `duration_days / 30.0` for all item line totals and total request amounts. When approved, these custom dates become the active `period_start` and `period_end` of `tenant_subscriptions` to anchor their initial cycle.
- **Catalog row editing & column visibility**: The operator Pricing Catalog edits catalog rows on a daily-price-first basis (monthly = daily × 30). For flat modules (`unit_price === null && included_qty === null`), the operator console hides the `Unit` and `Included` inputs (rendering empty spacer columns), providing only the daily rate editor.

## Numbers pool: Meta-account-driven bulk sync + quota locking (2026-08-06)
- **New discovery path, separate from the manual-add block above**: `POST /api/v1/numbers/sync-from-meta` (tenant-scoped) pulls every number registered on the tenant's connected Meta WABA via `meta_cloud.list_waba_phone_numbers` (`{waba_id}/phone_numbers` Graph edge) and imports any not already in `phone_numbers`, **regardless of `numbers_pool` quota**. Manual single-number `POST /api/v1/numbers` is unchanged and still hard-blocks at quota (`_numbers_pool_limit`/`numbers_pool_limit` in `numbers.py`/`numbers_pool.py`) — only the bulk Meta sync is allowed to bring in more than the tenant has purchased, landing the excess **locked** instead of rejecting it.
- **Locking is computed live, never stored** — `numbers_pool.py::compute_unlocked_ids(rows, limit)` is a pure function: `role="primary"` always wins a slot; the remaining `limit - 1` slots go to non-primary rows oldest-first by `created_at`; **if no primary exists yet, nothing is unlocked, regardless of `limit`** (oldest-first only ever fills slots *in addition to* a guaranteed primary slot). This means a brand-new tenant syncing 3 Meta numbers against a 1-number quota sees all 3 locked until they explicitly click "Set Primary" on one — the system never auto-picks by arbitrary Meta response order. It also means a subscription **downgrade** takes effect on the very next `GET`/routing decision with no re-sync needed, and the previously-primary number specifically (not just "the oldest") is what survives, since primary is the anchor, not age.
- **`get_unlocked_number_ids(db, tenant_id)`** (DB wrapper around the pure function) is the single shared choke point — used by `GET /api/v1/numbers/` (`locked` per row), `PATCH /{id}` (blocks `status="active"`/`paused_outbound=false` on a locked number; **`role="primary"` is always allowed** — it's the unlock action itself, swapping which number holds the slot), and `outbound_router.get_best_number()` (excludes locked candidates from real message routing — this is the layer that makes locking actually bite, since `get_best_number` picks among **any** `status=active` number today, not just `role=primary`). If you add a new place that selects a phone number for anything quota-sensitive, route it through this helper too, or a locked number could silently be used.
- **Locked standbys are NOT promoted (changed 2026-10-16)**: `number_health.standby_candidates` skips locked numbers, so failover never promotes a number the plan doesn't cover; with no unlocked candidate, broadcasts pause and the Red number keeps answering chats. Inbound messages to a locked number are received/logged normally; only outbound *selection* is gated.
- **Quality-value format**: resolved 2026-10-16 — one map, `number_health.map_quality`, takes GREEN/YELLOW/RED and HIGH/MEDIUM/LOW for every path (bulk sync, single sync, webhook).
- **Full design/plan**: `docs/superpowers/specs/2026-08-06-meta-numbers-pool-sync-locking-design.md`, `docs/superpowers/plans/2026-08-06-meta-numbers-pool-sync-locking.md`.

## Display name on a number is Meta's, not ours (2026-09-23)
- **`phone_numbers.display_name` is a mirror of Meta's `verified_name`, and both sync paths now overwrite it** — bulk `POST /numbers/sync-from-meta` (`numbers.py`, in the existing-row `updates` dict) and per-row `POST /numbers/{id}/sync-meta`. Before this change only *inserts* copied `verified_name`; existing rows kept whatever the row held forever, so a dashboard rename stuck and quietly diverged from the name customers actually see in WhatsApp. `meta_cloud.get_number_quality()` now requests `verified_name` alongside quality/tier for the per-row path — the daily `_sync_all_number_quality` scheduler job in `main.py` reads the same dict and simply ignores the extra key.
- **Guard that must stay**: both paths skip the write when `verified_name` is absent or blank. Meta omits it on some numbers, and the name is the card's only human-readable label — blanking it is worse than leaving it stale.
- **There is no rename path at all any more, on purpose.** The inline pencil on the Numbers page was removed (2026-09-23), `display_name` was dropped from the frontend `numbersApi.update` type, and **`display_name` was removed from `UpdatePhoneNumber` in `numbers.py`** — so `PATCH /api/v1/numbers/{id}` with only a `display_name` now 400s with "Nothing to update" (`test_numbers_locking_routes.py::test_rejects_rename_because_meta_owns_the_display_name` pins this). `POST /api/v1/numbers` still takes a `display_name` on create, which is fine: a row created before its first sync needs *some* label, and sync replaces it. Don't re-add the PATCH field — anything it wrote would be overwritten on the next sync anyway.
- **Renaming for real is a Meta review flow, not an edit** (verified against Meta's docs 2026-09-23, `developers.facebook.com/documentation/business-messaging/whatsapp/display-names`): `POST /{PHONE_NUMBER_ID}?new_display_name=…` → `new_name_status: PENDING_REVIEW` → `phone_number_name_update` webhook with `decision: APPROVED` → **you must then `POST /{PHONE_NUMBER_ID}/register` within 14 days** or the approval expires. Limit 10 changes per 30 days; an Official Business Account can't use the API path at all (Meta direct support only).
- **The blocker if anyone builds that flow**: the re-register step needs the number's 2-step PIN, and we generate it randomly and throw it away (`app_settings.py`, both the Embedded Signup and manual-token paths). Meta has no API to reset a PIN — only WhatsApp Manager's UI — so an automated re-register returns error 133005, which `meta_cloud.register_phone_number` currently swallows as "already registered". Either collect the PIN from the client or stop at "approved, now re-register in WhatsApp Manager".
- **Separate overwrite path worth knowing**: `app_settings.py::_upsert_onboarded_phone_number` writes `display_name` unconditionally onto a matching row, so reconnecting WhatsApp in Settings also resets the name from Meta. Since Meta is now the source of truth everywhere, this is consistent rather than a bug — but it was a live inconsistency while the pencil existed.

## Frontend CSS gotcha: absolute-positioned icon button inside a `relative` wrapper around an `<input>` (2026-07-31)
- `CalendarPanel.tsx`'s To-Do add-input had its `+` submit button (`absolute top-1/2 -translate-y-1/2`) visually centered too low, hanging below the input's rounded bottom edge. Cause: `<input>` is an inline-level replaced element, so a `relative` wrapper (`<form>` here) around a bare `<input>` inherits an invisible baseline "strut" from the font's line-box, making the wrapper's height taller than the input's own visible box — with the extra space landing below it. `top-1/2` centers against that taller invisible box, not the visible input. Fix: add `flex` to the wrapper (`className="relative flex group"`) so its height is driven purely by the input as a flex item, with no strut. Also fixed in the same pass: the input had `border-none` but no `outline-none`, so the browser's native focus outline (a heavy black rectangle) showed through instead of the intended `focus:ring-2 focus:ring-primary/20`. **Watch for this same pair of bugs anywhere else in the codebase that positions an absolute icon/button over a bare `<input>` inside a plain `relative` (non-flex) wrapper.**

## Frontend CSS gotcha: `100dvh`-relative `max-h` on an absolutely-positioned popover (2026-08-07)
- `AdPerformanceTab.tsx`'s "Columns" metrics popover (21 metrics) used `max-h-[calc(100dvh-7rem)]` on the dropdown panel, sized as if the panel started at the very top of the viewport. It doesn't — it's `absolute`-positioned under the trigger button, wherever that button sits on the page — so the calc let the panel claim far more height than the space actually below the button, and its lower rows ended up clipped/hidden depending on scroll position, with only a thin internal scrollbar as a hint anything was cut off. Fix: swapped to a fixed `max-h-[22rem]` (~352px, header + ~4-5 rows visible) with the existing `overflow-y-auto` on the inner list — deterministic regardless of where the trigger sits on the page. **Prefer a fixed rem cap over `dvh`-relative sizing for any absolutely-positioned dropdown/popover whose trigger isn't pinned to the viewport edge; `dvh` math only works for panels anchored at a fixed viewport position.** One other `calc(100dvh...)` usage exists in `frontend/app/dashboard/conversations/page.tsx:250,265`, but that's sizing a top-level page container to the viewport (a different, valid use), not a popover — not the same bug.

## Catalog AI disambiguation (2026-07-13) — do not confuse with the unrelated billing `feature_catalog`
- There are TWO unrelated things called "catalog" in this repo: (1) `dashboard/catalog` — the tenant-facing product/service catalog covered here, backed by `catalog_items`/`catalog_media`/`catalog_variant_groups`; (2) the operator's Pricing Catalog (`operator/subscription?tab=catalog`) — an internal billing SKU pricing tool backed by `feature_catalog`, see the itemized-subscriptions entries elsewhere in this file. Different tables, different audiences, only the English word overlaps.
- **The disambiguation gate (`classify_gate` in `catalog_retrieval.py`) only activates once a tenant has actually used variant grouping.** A contention set where every candidate has `variant_group_id: None` classifies as `"confident"` (pass the whole contention set to the prompt, no clarifying question) — this is deliberate, not a missed case: grouping is opt-in, and legacy/ungrouped tenants must keep pre-feature behavior (recommend from what matches, no new "which one?" friction). `same_group`/`broad_browse` only trigger once at least one non-null `variant_group_id` appears among the candidates.

There is no cascade-create — passing an arbitrary UUID to `create_item`/`update_item` 500s.
- **Partial embedding coverage is a live, accepted risk, not a bug** (see active-backlog.md) — `match_catalog_items` only returns items with `embedding is not null`, and the fail-open fallback ("list every ready item") only fires on **zero** candidates, not a partial subset. When debugging "why isn't disambiguation firing," check for that exact log line before assuming a data problem.
- No dev/test bypass exists for hitting these routes locally — `get_current_user` needs a real Supabase JWT (extract from the frontend's browser session/localStorage), and there's no webhook-simulation script for exercising `generate_reply()` end-to-end; calling it directly from a Python shell is the practical manual-test path.

## Client RBAC roles and user management (2026-07-12)
- **Adding a dashboard page = give it its own permission key (2026-10-08).** Don't gate a new page on an existing page's key — it then has no row in Roles and can't be switched on alone (that's how Deals, Meta Ads, Auto-Messages, Brain and Services went missing). - RBAC is tenant-scoped through `tenant_roles` plus `tenant_users.role_id`. A user has exactly one role. Owners remain legacy `tenant_users.role='owner'` and implicitly receive all permission keys; non-owner users resolve their role through `resolve_permissions()`.

Do not reintroduce a separate "Add Telecaller" path in Team unless the product model changes.

Reuse this pattern (session/flag lookup → dedicated system-prompt block) for any future "keep the AI live but change its behavior" need rather than muting via `ai_enabled`, which `ai_reply.py:840`'s own comment already flags as "a manual admin control only."
- **`intake.py`'s `_ACTIVE_STATUSES` includes `'paid'`** — without this, `_get_active_session()` would not treat an unresolved paid session as blocking, and a live AI could re-trigger `detect_intake_intent` into offering (and charging for) a **second** consultation on a lead who already paid and is just waiting for the astrologer. `route_intake()` has no explicit `if status == "paid":` branch — it falls through to the same `return False` "wait" behavior `awaiting_payment` already used, so the message still reaches `generate_reply()` normally.
- **Packages replace the single `amount_paise` fee (2026-08-13).** `normalize_packages(config)` auto-migrates any tenant still on the legacy single-fee config into one `{key: "standard", name: "Consultation"}` package at read time — never assume a tenant's config has a non-empty `packages` list; always go through `normalize_packages()`, not `config["packages"]` directly. New status `awaiting_package_choice` sits between `offer_pending` and `collecting`. `package_key`/`package_name`/`package_amount_paise` are snapshotted onto the session row at choice time (same reasoning as `field_schema` below) — repricing VIP in Settings must never rewrite what a past lead was actually charged.
- **`field_schema` is snapshotted per-row at collection time, not read live from config.** Field labels are free-text and deletable in Settings; without the snapshot, renaming or removing a field would retroactively relabel or blank out historical rows. `columns.ts` (frontend) and `intake_csv.py::build_csv_headers` (backend) both implement the identical "union of keys across rows, most-recent-snapshot-wins label" logic independently — if one changes, check the other, they must agree or the table and the CSV export disagree about what a column means.
- **Paid amount is read from the Razorpay webhook payload, never from the session's own `package_amount_paise`.** A lead can pay a payment link that staff just superseded via a package change in the drawer (the old Razorpay link stays live until Razorpay's cancel propagates). `confirm_intake_payment(amount_paid_paise=...)` sets `amount_mismatch=true` when the webhook amount disagrees with the snapshotted package price, surfaced as a ⚠ in the table/drawer — don't "fix" a mismatched row by trusting config over what was actually charged.
- **`_build_base_prompt()`'s APP LINK block is reference-only, not a standing instruction (fixed 2026-08-22, commit `5716c840`) — watch for the same shape of bug elsewhere.** It used to say "use this exact link whenever you need to share the app," unconditionally, for any tenant with `app_download_link` set — added by commit `35c590a2` (2026-07-20) before Intake existed, and completely independent of `intake_config.enabled`. Intake's astrologer-answer-redirect (`164f526c`) made `app_download_link` load-bearing on AstroTamil tenants for the first time, which woke this dormant block up and made it override each tenant's own master-prompt guidance on when to actually share a link — with intake fully disabled, since the two features only share a setting key, not any actual gating logic. General pattern to watch for: two independently-built pieces of prompt/tool context that read the same setting or lead state but were never made aware of each other. Two more instances of the same pattern found and fixed the same session: `catalog_tools` (the `recommend_catalog_item` function-calling tool) stayed live and callable during an active paid/in-progress intake session — a tool schema doesn't read the "don't re-offer" prose in `_intake_paid_prompt_block`/`_intake_in_progress_prompt_block`, so `generate_reply()` now explicitly drops `catalog_tools` when `build_reply_system_prompt()` reports `intake_active`. And the escalation (`needs_human_attention`) and intake holding blocks could both fire on one reply, stacking two redundant "someone will get back to you" messages — intake is now checked first and escalation is skipped when intake already covered the turn. See `.agents/decisions/log.md` 2026-08-22 entry.
- **`service_noun` (default `"consultation"`) is substituted into exactly three hardcoded lead-facing strings**: the WhatsApp payment receipt (`routes/intake.py`), the Razorpay payment-link description (`services/intake.py`), and `_intake_paid_prompt_block()` in `ai_reply.py`. These three do NOT go through the AI's normal tunable prompt — if a tenant reports the wrong word showing up post-payment, check these three call sites, not the AI tune settings. The package price list itself is rendered in Python from config (`package_list_message()`) — deliberately never generated by the LLM, since a hallucinated price is a real liability.
- **`intake_sessions` list/CSV endpoints validate `q`/`cursor` against a strict allowlist regex, not escaping**, because both are interpolated into PostgREST `or_()` filter strings rather than bound as parameters (2026-08-13 security-review fix). If extending the filter logic, keep using `.eq()`/`.in_()` for anything that must stay parameterized — don't add more raw string interpolation into `or_()` without the same allowlist treatment.
- **CSV export sanitizes formula-injection prefixes (`=+-@`/tab/CR) on lead-supplied free text and field labels, but deliberately NOT on phone** (`intake_csv.py::_csv_safe`) — phone is a structured E.164 identifier, not free text, and quote-prefixing every phone number to guard against a non-exploitable leading `+` would corrupt data the client explicitly wants clean in the export. If adding new CSV columns from lead-controlled input, sanitize; if adding structured/system-derived fields (IDs, phone, status enums), don't.
- **Marking a session resolved**: `resolve_intake_session(session_id, tenant_id)` transitions `paid → resolved` (only from `paid`), via `PATCH /api/v1/intake/sessions/{id}/resolve` (permission: `conversations.reply`, matching `chat_handovers.py`'s own `/resolve` endpoint convention — there is no separate `conversations.manage`). Once resolved, `get_paid_unresolved_session()` stops finding it, so the AI reassurance prompt block stops applying. Unlike the pre-rename version, Resolved rows stay visible in the Intake table (Resolved filter chip) rather than vanishing — the old bucket-only endpoint made this unauditable.
- **`/dashboard/intake` does not embed the full lead `ChatThread`** (removed pre-rename, 2026-08-12) — it's a "who paid and what did they submit" surface, not a reply UI. The drawer (`IntakeDrawer.tsx`) renders `collected_data` as a table plus payment info, package override, and "Mark Resolved". If a future need for in-line staff replies on this page comes up, re-litigate rather than assuming the old `ChatThread` embed should come back.
- **`Astro Tamil` (`eba3ed94-277c-430f-a992-19bbe855e2f4`) and `Astro Tamil - Co` (`9dfe3f53-a4f8-4c0e-99b5-853b42556ee8`) are separate tenant rows for sister companies, each with independently-configured `intake_config`/master prompt/Razorpay settings — but they're meant to run the same KB and master-prompt content, kept in sync by hand, not automatically.** A whole debugging session (2026-08-11/12) was initially scoped against the wrong one before the mismatch was caught. A 2026-08-22 session quoted `Astro Tamil`'s master prompt as evidence for a bug actually reported against `Astro Tamil - Co`'s WhatsApp number — not a wrong-tenant diagnosis (the underlying code bug and fix were correct for both), but the prompt text cited mid-session was stale on the target tenant because a prompt update had been made to `Astro Tamil` and not yet copied to `Astro Tamil - Co`. Before trusting any Supabase query result or quoting prompt/config text for this account, confirm the tenant_id via the actual WhatsApp number against `phone_numbers.number` (or `meta_phone_number_id` → `phone_numbers.tenant_id`, visible in Render logs) — don't assume a name match, and don't assume the two tenants' KB/prompt content currently matches even though it's supposed to. `Astro Tamil - Co` is the one with live Razorpay keys as of the 2026-08-11/12 session; `Astro Tamil` does not. **`Astro Tamil` (no "- Co") is a teammate's tenant (`keerthivs2805@gmail.com` owner) used for testing, not this repo's primary user's own account — as of 2026-08-25 it was `enabled: false` with empty `packages`/`fields`/`trigger_description` until seeded for a testing session.**
- **Nested packages (migration 186, 2026-08-25) — the addon offer must never infer "what was picked" from the customer's raw last message.** A package tree can nest to any depth (`options: [...]` on a non-leaf node); a level with exactly one *active* child (`_resolve_choice()`) auto-skips straight through without asking again. This means the customer's `body` text at the moment a leaf is finally reached can still name an ancestor branch, not the leaf itself (e.g. tapped "Career Reading," silently landed on "General Career Reading" underneath). `_send_menu()`'s `selected` param exists specifically to break this: pass the *resolved* leaf so its name+price get Python-rendered into the block ahead of the addon list, rather than trusting the composer to guess it from `customer_message`. Any new call site that shows a menu right after an auto-skip needs the same treatment — the bug wasn't in the auto-skip logic, it was in every downstream message assuming `customer_message` still described the current state.
- **Addon choice (`awaiting_addon_choice`) must resolve on an explicit decline or a real match — never on "nothing matched."** `match_addons()` returns an empty list for two different reasons that look identical from the caller's side: an explicit decline word, or a genuinely ambiguous/off-topic reply that matched nothing. The route_intake handler checks `body.strip().lower() in _ADDON_DECLINE_WORDS` **before** calling `match_addons()` specifically to keep these apart — treating an empty result as "customer declined" (the pre-2026-08-25 bug) silently drops the addon opportunity on any confused reply with zero warning. If extending this handler, keep computing `is_decline` explicitly rather than trusting `chosen_addons == []` to mean anything on its own.
- **Payment amount is `total_amount_paise` (package + addons), never `package_amount_paise` alone — this was a real live money bug until 2026-08-25.** Both the Razorpay link-creation call and `confirm_intake_payment()`'s `amount_mismatch` check must read the same field, or the mismatch check silently stops meaning anything (it'll match whatever the link was wrongly created with). `package_amount_paise` alone is only correct as a fallback for sessions that predate the addons feature and never got `total_amount_paise` set.
- **The synthetic "No thanks" addon option (`_NO_ADDONS_OPTION`) must be folded into the level *before* `_tap_mode()` runs, not after.** It counts as a real item toward the 2–3 (buttons) / 4–10 (list) tier boundaries — appending it after the tier is already decided risks a 3-real-addon menu becoming a 4-button send, which exceeds WhatsApp's hard cap. `_tap_mode`/`_build_buttons`/`_build_list_sections` don't need to know this option is synthetic; they just treat it as another node with a `key`/`name`.

## Meta Embedded Signup / Facebook Login for Business — the token is a SYSTEM_USER, and `me/*` is a lie (2026-08-14)

- **The code exchange returns a business-integration *system user* token, not a personal user token.** Verified live against Meta 2026-08-14: `debug_token` on a real signup token reports `type: SYSTEM_USER`, `application: AIRA`, `expires_at: 0` (never expires), `user_id` = "AIRA System User". **Consequence: every `me/*` edge is dead.** `me/accounts` returns HTTP **200 with `{"data": []}`** — not an error, an empty success, which is what made this so slow to diagnose. `me/adaccounts` → `(#100) Unsupported get request`. `me/businesses` → `(#100) Missing Permission`. `/{business_id}/client_pages` → `(#200) Requires business_management`. Do NOT "fix" a missing-asset bug by reaching for another `me/` edge; they all fail this way.
- **CORRECTION (2026-10-02) — `me/*` is NOT always dead, and granular scopes are NOT always populated.** The live Astro Tamil unified signup (Nira config, ads_read now approved) logged `type=SYSTEM_USER` with `granted_assets={'pages_show_list': 0, 'ads_read': 0, 'pages_messaging': 0, ..., 'whatsapp_business_management': 2}` — permissions granted with **zero target_ids** — yet the Page still connected, which can only have come from `me/accounts`. Ad accounts had no `me/` fallback, so the picker showed only "Do not connect". Fix `4b7d258e`: `_list_token_edge()` now merges `me/accounts` AND `me/adaccounts` into the granular-scope results (best-effort, never raises; regression test `test_ad_accounts_come_from_me_adaccounts_when_ads_grant_has_no_target_ids`). After deploy + reconnect the ad account (`act_905982549234446`, "Astro Tamil Test") connected. Not yet seen: the log line proving which source supplied it — if a future signup misses it, grep `me/adaccounts is not readable` (it now logs Meta's error). Keep both sources; neither is reliable alone.
- **The granted assets live ONLY in the token's granular scopes.** `discover_business_login_assets()` (`services/meta_cloud.py`) calls `GET /debug_token` and reads `granular_scopes[].target_ids`, then fetches each asset by id (`GET /{page_id}?fields=id,name,access_token,instagram_business_account{...}`). `me/accounts` is retained as a **best-effort merge only** (`_list_user_token_pages`, never raises) because some Login configurations still issue a real user token — it can add Pages, never fail a signup.
- **Ad-account ids arrive bare in the grant** (`"42"`, not `"act_42"`) and are only readable as `act_<id>` — `_as_ad_account_id()` normalizes. Instagram scopes (`instagram_basic`, `instagram_manage_messages`) report **Page** ids as their targets, not IG ids, so they're grouped with the Page scopes in `_PAGE_GRANT_SCOPES`.
- **Meta's asset picker is NOT a permission grant — this is the single most confusing thing here.** The signup window shows a Page/Instagram/Catalogue/Ad-account picker driven by the *configuration's asset setup*, and the review screen will cheerfully say "Facebook Page — <name>". But the issued token only carries the permissions the configuration **requests**. As of 2026-08-14 the unified config (`NEXT_PUBLIC_META_UNIFIED_CONFIG_ID`, `2026693308738446`) requests **WhatsApp only** — every signup token comes back with `scopes: whatsapp_business_management, whatsapp_business_messaging, public_profile` and zero page/IG/ads targets. So a user can select a Page, see it confirmed on Meta's own review screen, and the app still receives no authority over it. **If Messenger/Instagram/Ads "won't connect", check `granular_scopes` in the Render log line before touching any code.**
- **`meta_cloud.py` logs the verdict on every signup**: `Meta signup token type=... scopes=... granted_assets={scope: count}`. This one line answers "did Meta actually grant it" in seconds — always read it first.
- **A missing Page must never fail the signup.** WhatsApp onboarding is independent of Pages; `page_id` is optional on `UnifiedMetaSignupCompleteRequest` and the handler skips the Page claim, the Page webhook subscription, and all `facebook_*`/`instagram_*` settings when absent. Instagram DM is never connected "through Instagram" — it rides on the linked Page's access token, so **no Page → no Instagram, always**.
- **The webhook verify token is the one credential Meta never returns.** It's a string *we* choose and paste into the Meta app's webhook settings; Meta echoes it back as `hub.verify_token`. There is nothing to fetch, which is why embedded signup left the field blank and someone hand-pasted it (2026-08-14). WhatsApp tolerates a missing per-tenant row — `routes/webhook.py` checks every tenant's stored token then falls back to `settings.meta_verify_token` — but **`routes/facebook.py:21` and `routes/instagram.py:21` call `get_setting("meta_webhook_verify_token", tenant_id=...)` with no fallback, and `get_setting` has no env fallback by design**, so those challenges 403 forever without the row. `_save_shared_meta_app_credentials()` now writes both `meta_app_secret` and `meta_webhook_verify_token` from env at connect time, on all four connect paths. **Requires `META_VERIFY_TOKEN` to be set on Render** — if it's unset the helper silently writes nothing.
- **`maybe_single().execute()` returns `None` when nothing matches — not a row object with `data=None`.** This 500'd the whole unified completion for any first-time phone number (`AttributeError: 'NoneType' object has no attribute 'data'`, confirmed in Render logs 2026-08-14 18:47/18:48). The codebase idiom everywhere else is `if row and row.data` / `(x.data or {})`. **Still latent at `routes/calls.py:155` and `routes/calls.py:239`** — see active-backlog.md.

- **The wire contract is not ours to tidy.** Paths, header names (`X-API-Key` out, `X-Astro-Signature` back), payload keys and the `{session_id}::f{n}` ref format are shared with the astrobackmatrimony Django app, written by Ansar Ibrahim and already deployed against them. Renaming anything that crosses the wire breaks both systems, and the failure is invisible until a paying customer gets silence. Aira-internal names (`intake_sessions`, `confirm_intake_payment`) are free to change; the payload is not.
- **The reply callback depends on the legacy route alias.** Django calls `/api/v1/expert-handoff/astro-reply`. That path exists only because `main.py` still mounts the pre-rename prefix alongside `/api/v1/intake`. Removing the alias as "dead legacy" would break inbound replies while every outbound push kept working — the worst shape of failure, since the dashboard still fills up.
- **`push_consultation` refuses rather than guesses.** Django does not normalise: a birth date it can't split raises, and a gender that isn't exactly `M`/`F` silently becomes `M`. `astro_normalize.py` therefore returns `None` for anything it can't parse, and the push is abandoned with the unusable fields named in the log. A wrong horoscope is worse than no horoscope — do not "fix" this by defaulting.
- **The push is best-effort by design, and `astro-push-reconcile` (5 min) is what makes that safe.** A bridge outage during the one webhook that flips a session to `paid` would otherwise strand the consultation forever: the paid transition is idempotent and never re-fires. The sweep re-drives paid sessions with `astro_question_id IS NULL` for 3 days. Django is idempotent on the session id, so re-driving is always safe.
- **The astrologer's answer is never sent to the customer (changed same day, migration 181).** WhatsApp carries one short nudge — "your answer is ready, open the app and sign in with this number" — and the reading is read inside the AstroTamil app. `reply_image_url`/`reply_voice_url` are ignored and the media relay was deleted; `reply_text` is archived on `intake_sessions.astro_last_reply_text` for support only, deliberately **not** in `messages`, which records what the customer actually received.
- **The app link is appended in code, never composed by the model** (`_compose_reply_nudge`, reading the `app_download_link` setting). A model that invents a download URL sends a paying customer nowhere — commit `24494b3d` fixed that exact failure once already on the offer message. The same ban is written into `_intake_paid_prompt_block`.
- **`astro_last_reply_id` is claimed *before* sending, not after** (`.or_(is.null, lt.<id>)` — monotonic, so a replayed older reply is also a duplicate), and **rolled back if the nudge fails to send**. Without the rollback the claim blocks every retry and the customer never learns an answer exists.
- **There are no WhatsApp follow-ups, by decision.** Follow-up questions happen inside the app. `push_followup()`, `forward_followup_to_astrologer()`, the `route_intake` branch and `astro_followup_count` all existed for about a day (migration 180) and were removed by 181. Do not rebuild them without checking whether the app still owns that conversation.
- **No 24-hour window check and no staff alert on it, by explicit decision.** The astrologer answers same-day in practice, and anything later is the app's problem. If that ever breaks, the fix is a WhatsApp **template** for the nudge — its text is fixed, so unlike a free-form reading it qualifies — not reinstating the check.
- **Between payment and the nudge the AI stays live and must not promise a WhatsApp answer.** `_intake_paid_prompt_block(service_noun, answer_in_app=...)` switches on whether the tenant has an `app_download_link`; the payment receipt no longer mentions WhatsApp at all, and deliberately does not mention the app either — telling someone to download it before their answer exists earns a bad review.
- **A rejected reply is the only bridge failure with no other symptom.** 401 + one log line, astrologer's screen says "sent", customer hears nothing. `alert_bridge_auth_failure()` exists solely to give that failure a voice; it deliberately alerts only after the ref resolves to a real session (so the public endpoint can't be used to spam staff) and deliberately alerts anyway if its own rate-limit lookup fails.
- **`reply_source` stays `'expert_handoff'`** on bridge-delivered messages. It's a hand-maintained CHECK constraint value (migration 173); the feature was renamed but the stored value was left alone on purpose — changing it needs a constraint migration first (see the Intake section above for how that bit once already).
- **Nothing here has run against a real Django instance.** All bridge tests use a fake HTTP client. `astro_bridge_url`/`api_key`/`secret` are unset for every tenant, so the bridge silently no-ops today. Treat the first live run as untested on both sides, not just ours.
- **The package tier is not sent.** The astrologer receives `amount` in rupees but not which package was bought. If tiers ever mean different depth of reading, that gap matters.
- **Send-then-log ordering causes double replies — fixed 2026-08-19 (commit `5341d57a`), watch for the pattern elsewhere.** `intake.py`'s `_send_and_log` sent the WhatsApp message before logging it. A logging failure after a successful send (e.g. hitting `messages_reply_source_check`) raised past the point where the message already reached the customer, so the caller (`route_intake`) reported the turn as unconsumed, and `generate_reply` ran anyway and sent a second, unrelated reply on top of it. General rule: if send and log are two steps, a failure between them must never look like "nothing happened" to the caller — either log first, or make the post-send step non-fatal so the send is never silently retried.
- **Brain-led intake is parked, not deleted (2026-08-19).** `services/intake_brain.py` — let `generate_reply` drive paid intake via function-calling instead of `route_intake` composing every line — is stripped from `main` and lives on branch `feature/brain-led-intake`. It was gated to one phone number, never live-verified beyond that, and was the source of most of `generate_reply`'s added complexity. `route_intake` (composer-led) is the only live path. Don't assume `intake_brain_led_phones` app_setting does anything on main.
- **Credentials are ops-entered in the operator console, not client-facing (2026-08-23).** `astro_bridge_url`/`api_key`/`secret` are set in `frontend/app/operator/(console)/client/[id]/views/config.tsx`'s "Astro Bridge" section (backend `GET/PATCH /clients/{tenant_id}/config` in `operator.py`) — not in the client's own Settings → Connect Channels. A client-dashboard card for this existed for one session and was removed; don't re-add it without re-reading this note. Reasoning: these values are issued by / coordinated with the astrologer's own Django devs during setup, not something a client's staff can self-serve the way they paste their own Razorpay key.
- **`tenants.enabled_features` flag `astro_bridge` gates nothing backend-side.** `_bridge_config()` only checks whether the 3 settings are actually filled in — the flag is purely a visibility/bookkeeping marker, toggled via the operator console's generic "Custom Feature Flags" panel (same `config.tsx`, reuses `PATCH /clients/{id}/features`). Currently set on Astro Tamil (`eba3ed94-277c-430f-a992-19bbe855e2f4`) and Astro Tamil - Co (`9dfe3f53-a4f8-4c0e-99b5-853b42556ee8`) only.

## `slowapi`'s rate-limit middleware breaks any multi-chunk `StreamingResponse` (2026-08-22)

- **`slowapi==0.1.10`'s `_ASGIMiddlewareResponder.send_wrapper` (`slowapi/middleware.py`) re-sends the buffered `http.response.start` on every `http.response.body` message, with no "already sent" guard.** It intentionally holds back the start message so it can inject rate-limit headers once the first body chunk confirms status/headers — fine for a normal one-shot `Response` (exactly one body message). Breaks on `StreamingResponse`: Starlette always sends a second, empty closing body message after the content, so the wrapper resends `http.response.start` a second time, and Starlette's `BaseHTTPMiddleware` (silently present via FastAPI's `@app.middleware("http")` decorator on `server_error_json_middleware` in `main.py`) chokes on the duplicate with `AssertionError: Unexpected message`. No newer `slowapi` release exists to fix this (0.1.10 is latest on PyPI as of this session).
- **Fix used on `/analytics/compare/export` and `/intake/sessions.csv`**: both routes already built the whole CSV in memory (`io.StringIO()` → `.getvalue()`) before wrapping it in `StreamingResponse` — they never needed streaming semantics. Swapped to a plain `Response(content, media_type=..., headers=...)`, which sends exactly one body message and never triggers the bug.
- **Any future route that genuinely needs incremental streaming** (can't fully materialize in memory first) will hit this the same way as long as it sits behind the global rate limiter. Either exempt that route from `SlowAPIASGIMiddleware`, or don't add a second one without checking this first.

## WhatsApp typing indicator + quoted-reply tagging (2026-08-23)

- **Typing bubble**: `send_typing_indicator()` in `services/meta_cloud.py` fires the Cloud API's `status: "read"` + `typing_indicator: {"type": "text"}` call right before `route_intake`/`generate_reply` in `webhook.py`'s `_process_inbound_message_background`. Shows WhatsApp's "typing…" instead of the reply just popping in. Best-effort, never raises — a failed indicator must never block the actual reply. Meta auto-dismisses it after 25s or on the next message send, whichever first. Committed and pushed (`49af8580`).
- **Quoted-reply tagging is deliberately narrow — only fires on out-of-order replies, not every message.** `generate_reply()` (`services/ai_reply.py`) takes the triggering `meta_message_id`; right before sending, it checks the lead's newest inbound message row. If a newer message already landed while this reply was generating (lead sent a second text before the first reply finished), the reply is sent with `context: {message_id: <original>}` so it visibly quotes the question it's answering instead of looking like it answered the newer one. If no newer message exists (the normal case), no tag — matches current behavior exactly.
- **Why check at send time, not at receive time**: the race is inherent — two `_process_inbound_message_background` calls run concurrently per inbound message (`BackgroundTasks`, no debounce/batching exists), so LLM latency alone decides which reply lands first. Querying "what's the newest inbound message right now" at the moment of send is the only point that reflects reality.
- **Scope**: WhatsApp text replies only (`send_whatsapp` → `send_text_message`). Voice replies and other channels (Instagram/Telegram/Facebook) don't have this — not asked for, not wired.

## Analytics: ad attribution lives on the message, not the lead; IST is not the default anywhere it should be (2026-08-23)

## Silence nudge (`services/silence_nudge.py`, 2026-08-23) — and the two schema values it proved wrong

- **An OPEN `chat_handovers` row has `status='pending'`, NOT `'open'`.** The table defaults to `'pending'` (migration 043) and `resolve_handover()` flips it to `'resolved'` — those are the only two values that exist live (verified against prod 2026-08-23). `ai_reply.py`'s `_trigger_chat_escalation` even comments a `status='pending'` row as "already has an open handover". **Any new "is this lead escalated?" check that queries `'open'` matches zero rows and silently disables itself** — which is exactly what the silence-nudge plan originally specified before it was caught pre-merge. There is a regression test pinning this (`test_open_handover_query_uses_pending_status`).
- **Live `intake_sessions.status` values are a subset of the constraint.** Migration 176's check allows 8; only `cancelled, collecting, offer_pending, paid, resolved` appear in prod so far. Terminal = `resolved`/`cancelled`. `_ACTIVE_INTAKE_STATUSES` lists all 6 non-terminal values (not just the live 3) so it doesn't quietly break when `awaiting_payment` etc. start appearing.
- **Correctness is `_thread_unchanged()`, not `cancel_pending()`.** The fire-time re-check ("is our `anchor_message_id` still the newest message for this lead?") is what prevents a nudge landing on top of a reply. The inbound-webhook cancel hooks are a queue-hygiene optimisation only. This is deliberate: it means a missed cancel site costs a wasted row, never a wrong send, so new inbound paths don't have to be exhaustively hooked to stay safe.
- **A ladder rung must re-anchor on the nudge it just sent.** After sending, that nudge *is* the newest message, so arming rung N+1 against the original AI reply makes `_thread_unchanged()` fail instantly and the second rung never fires — presenting as a config problem, not a bug. `_process_job` reads the id back off the `messages` insert for this. Test: `test_drain_arms_next_rung_anchored_to_the_nudge_it_just_sent`.
- **`silence_nudge_delays` values are gaps, not offsets (2026-09-22).** Rung 0 waits N minutes after the AI reply; each later rung waits from the *previous nudge* (the re-arm above). So `"5,60"` = 10:05 then 11:05, not 10:05 then 11:00, and the old "must strictly increase" rule was meaningless — dropped in `_parse_delays` and `parseSilenceDelays.ts` (`"60,5"` is now valid). The settings page edits this as one row per reminder ("Send [N] minutes after reminder N-1", max 3) and still stores the comma string. Keep both parsers in sync; they reject/fallback differently on purpose (UI blocks save, backend falls back to `[5]`).
- **`_send_reengagement()` does NOT gate on `ai_enabled`, `converted_at`, or `blocked_at`** — only `phone`, `whatsapp_undeliverable`, `opted_out` (plus the master switch). `automation_guards.py` therefore covers *only those three*, because widening the shared helper would have silently changed re-engagement's behaviour. `silence_nudge` performs the other three itself. If you ever extend `automation_guards`, check both callers — the asymmetry is intentional, not an oversight. See backlog for whether re-engagement *should* have them.
- **Gates 1-2 (feature switch, `ai_auto_reply_enabled`) return HOLD, not SKIP** — the job stays `pending` so automation resumes cleanly when a tenant flips the switch back on, matching `_send_reengagement`'s deliberate no-log-row-on-master-switch-skip. Only lead-level blockers consume the job.
- **The first ladder rung ignores quiet hours by design**; only later rungs defer to the window's end. A lead who messaged 5 minutes ago is demonstrably awake — see `[[decisions/log.md]]` 2026-08-23.

## `generate_reply`'s LLM `try` block does not return on exception

Load-bearing, and it has already caused one live bug. The `except Exception` around the LLM call sets a fallback `reply_text` and **falls through** to the channel dispatch below. Any variable bound only *inside* that `try` is unbound on the exception path — and the dispatch reads several of them.

This shipped broken: `catalog_images_to_send` was assigned inside the try and read after it, so **every LLM failure on a WhatsApp lead raised `NameError` instead of sending the fallback, and the lead got nothing.** Fixed 2026-08-24; `chosen_block` and `catalog_images_to_send` are now bound before the `try`, guarded by a regression test that asserts their position in the source. **If you add a variable that the send/dispatch path reads, bind it before the `try`.**


## Source-text assertion tests break on reformatting, not on regressions (2026-08-25)

Several backend tests assert on the **source text** of a function rather than its
behaviour — e.g. `assert "send_whatsapp(_wa_phone, reply_text" in source`. They exist
because the real call is buried in `generate_reply`'s dispatch and is expensive to
exercise, so the contract is checked statically instead.

- **They fail on formatting alone.** Reflowing a call across lines, or adding a keyword
  argument, breaks the literal match while the behaviour is untouched. This produced 3
  red `Backend Tests` runs on `main` that looked like product bugs and were not.
- **Fix them with `ast`, not by loosening the string.** Parse the source, walk for the
  `ast.Call` node, and assert on its args/keywords. Survives reflow and added kwargs.
- **Quantify over ALL matching call sites, not `any()`.** `ai_reply.py` has **two**
  text-reply dispatches (the ordinary path and the quick-reply-block fallback). An
  `any(...)` assertion was verified to stay **green** with `phone_number_id` deleted from
  one of them — exactly the regression the test exists to catch. Collect the dispatches,
  then assert none of them is missing the argument, and name the offending `lineno`.
- **Always test the test.** Inject the regression, confirm the assertion fails, restore.
  A loosened assertion that cannot fail is worse than no test.

`frontend/app/dashboard/settings/SettingsSection.tsx` holds both the card

## Meta webhook signature verification — which app's secret signs what (2026-08-30)

Every inbound Meta webhook is HMAC-checked in `services/meta_webhook_verify.py` against a secret
read from `app_settings`. The rule that trips people up: the secret belongs to the **Meta app that
owns the webhook subscription**, not to the channel or the tenant.

- `meta_app_secret` is **app-level, not tenant-level**. `_save_shared_meta_app_credentials()`
  copies it (and `meta_webhook_verify_token`) from the backend's env onto every tenant at connect
  time, so all tenants hold the identical value. WhatsApp (`routes/webhook.py`) and Facebook
  (`routes/facebook.py`) verify against it and have **no per-channel override**.
- Instagram alone has one: `verify_meta_signature(..., secret_key="instagram_app_secret")`, falling
  back to `meta_app_secret` when that key is empty. It exists for the Instagram-Login
  (`graph.instagram.com`) flavour, which is signed by a different secret.
- **Therefore**: configuring a channel's webhook in a Meta app other than the one whose secret is in
  the backend env silently 403s every event. On 2026-08-29 a Page/Instagram webhook was configured
  in a "Test Aira" app (`2915845815438559`, app secret md5 `b1779b33…`) while the backend held a
  third app's secret (md5 `0bc23dc7…`, the one WhatsApp runs on) — a continuous 403 flood with no
  other symptom.
- **The verify-token GET proves nothing about app identity.** `verify_instagram_webhook` /
  `verify_facebook_webhook` only compare `hub.verify_token` to the tenant setting, so *any* app that
  pastes the right URL and token passes "Verify and save". Only the signed POST discriminates.
- **How to diagnose**: compare `md5(value)` of `meta_app_secret` / `instagram_app_secret` in
  `app_settings` against the secret at Meta → App settings → Basic. A WhatsApp POST returning 200
  **with no accompanying WARNING** proves the stored secret is valid for whichever app sends
  WhatsApp — all three drop paths in `routes/webhook.py` log a warning before returning 200.

**Instagram must be the Facebook-Login flavour.** `send_instagram()` posts to
`graph.facebook.com/v21.0/me/messages` with a **Page** access token, and activation subscribes on the
same host — nothing in the codebase calls `graph.instagram.com`. So `instagram_access_token` holds a
*Page* token (the embedded flow writes the same token to both channels) and `instagram_app_secret`
should be left **blank**. `instagram_page_id` must hold the IG business account id (`17841…`),
because that is what arrives as `entry.id` and what `resolve_tenant_for_page()` matches — a mismatch
skips the entry with a "belongs to tenant X, not Y" warning and looks exactly like nothing happening.

**One tenant per Meta app.** The IG/FB callback URLs carry `tenant_id` in the path, but a Meta app
allows only one callback URL per webhook object — so one Meta app serves Instagram/Messenger for
exactly **one** tenant. WhatsApp has no such limit: `/webhook/whatsapp` takes no tenant and resolves
it from the payload (`_resolve_tenant_from_payload`).

## debug_token: Meta's refusal *is* the answer (2026-08-30)

`_resolve_token_app_id()` in `routes/app_settings.py` identifies which Meta app issued an access
token, so `activate_channel` can refuse a token from the wrong app. The trap is what Meta returns
for a **foreign** token — the case the check exists for:

```
GET /v21.0/debug_token?input_token=<Test Aira token>&access_token=<AIRA app token>
→ 400  (#100) The App_id in the input_token did not match the Viewing App
```

Meta does **not** return `data.app_id` with a differing value. It returns no data at all, plus that
error. A first implementation treated "no data" as inconclusive and failed open, so a Test Aira
token activated cleanly on 2026-08-30 12:21 — the guard silently skipping the exact scenario it was
written for. The function now returns `(app_id, is_foreign)` and matches that message
case-insensitively; every other error path still fails open so a Graph outage cannot block
onboarding.

**Two Meta apps have near-identical names**, which is worth knowing before reading any log:

| Name | App ID | Status |
|---|---|---|
| `Test Aira` | `2915845815438559` | Development, no privacy policy, **not** review-ready |
| `AIRA` | `2225044871604460` | Published, Bloom Matrix, **the app the backend trusts** |

Always cite the **ID**. `META_APP_ID` / `META_APP_SECRET` in Render are AIRA's; the backend has never
heard of Test Aira, so anything configured there is discarded at the signature check.

**Capability errors look like scope errors but are not.** With a Test Aira token,
`POST /{ig-account-id}/subscribed_apps` returns `(#3) Application does not have the capability to
make this API call.` That is the *app* lacking Instagram messaging capability, not the token lacking
scopes — the frontend's "check token scopes" hint is misleading here.

## Graph API credentials leak through httpx's request log (2026-09-01)

Meta's Graph API takes credentials as **query parameters**, and `httpx` logs every request URL at
INFO including the query string. That put the Meta app secret — inside the `{app_id}|{secret}` app
access token — and every Page access token into Render's logs in plaintext:

```
HTTP Request: GET .../debug_token?input_token=EAApb8kIM…&access_token=2225044871604460|366a9b73…
```

Enough to forge webhook signatures for every tenant. `main.py` now sets the `httpx` logger to
WARNING; our own log lines are unaffected, and `test_httpx_logging_muted.py` imports the app and
asserts the logger is genuinely quiet at INFO so it cannot silently regress.

**The rule to carry**: any new Graph call passing a secret as a query param re-opens this the moment
someone raises httpx's level. Prefer checking what a new outbound call logs before shipping it —
this was found only by reading production logs for an unrelated reason.

## Who owns a Page access token (2026-09-01)

A recurring point of confusion worth stating plainly: a Page access token has **two** owners.

- **Which Page it controls** — the client's.
- **Which app issued it** — always Aira's (`2225044871604460`). Clients have no Meta app.

The issuing app decides what the token may do (its approved permissions) *and* whose app secret
signs the resulting webhooks. So a token must always be minted through Aira's app, never from
anything client-side — but it grants access to the client's Page, which means a Page admin has to
approve it. Either the client approves through the Embedded Signup popup (normal), or the client
grants Aira an Admin/Partner role on their Page first and it is minted by hand (debugging only).
Manual onboarding is therefore not merely "paste a token" — without a Page role there is nothing to
generate, because Meta will not show that Page.

## Login config: asset scope is not permission scope — Nira shipped without `pages_manage_metadata` (2026-09-04)

Sharper version of the 2026-09-01 note above. Knowing a config "requests Pages" is not enough —
each individual Page permission the code's Graph calls need must be ticked separately in the
configuration's **Permissions** step, and a missing one fails silently.

`META_UNIFIED_CONFIG_ID` (`2026693308738446`, "Nira - Bloom Matrix") requested Pages as an
**asset** and carried `pages_show_list` + `pages_messaging`, but **not `pages_manage_metadata`**.
Consequence: `POST /{page_id}/subscribed_apps` (`app_settings.py:1288`, `:1585`) could never
succeed, so a Facebook/Instagram Page would appear to connect while its messaging webhook was
never subscribed — inbound Messenger and IG DMs silently never arrive. Nothing in the UI surfaces
this; the failure is a `logger.warning` on the `subscribed_apps` response. Fixed 2026-09-04 by
adding the permission to the configuration (no code change).

**The rule:** every Graph endpoint the backend calls maps to a permission that must be present in
the *specific config id the frontend passes*. The mapping as of 2026-09-04:

| Call | Permission |
|---|---|
| `GET /me/accounts?fields=…,instagram_business_account` | `pages_show_list`, `instagram_basic` |
| `POST /{page_id}/subscribed_apps` | `pages_manage_metadata` |
| `POST /me/messages` (Messenger + IG) | `pages_messaging`, `instagram_manage_messages` |
| `GET /{ad_account}/insights` | `ads_read` |
| `POST /{waba_id}/subscribed_apps`, templates | `whatsapp_business_management` |

**Three configs exist and only two are wired to code.** `useMetaSignup.ts:10` defaults to Nira
(`2026693308738446`) and `:16` to Aira (`1063294086656120`, coexistence). **Mira**
(`2226622718102220`) is referenced nowhere in the current frontend — it is an orphan carrying
`ads_management` and `pages_manage_ads`, neither of which any code calls. Don't "fix" a connect
bug by editing Mira; check `useMetaSignup.ts` for the id actually in play first. (This exact
mistake cost a round-trip on 2026-09-04.)

**Diagnosing a grant that looks complete but isn't:** run `debug_token?input_token=<token>` in the
Graph API Explorer. A scope listed in `scopes` but appearing in `granular_scopes` **with no
`target_ids`** means the permission was granted with zero assets attached — e.g. the account holds
no Page at all. That is a different failure from the permission being absent, and it looks
identical from the app's side (`me/accounts` returns `{"data": []}` either way).

## Embedded Signup: every asset in a configuration is MANDATORY — hence four configs (2026-09-06)

**Supersedes the "three configs, Mira is an orphan" note above.** Mira is wired now, and a
fourth config exists.

**The finding that drove all of it:** Meta's signup window will not enable **Next** until every
asset listed in the login configuration has been selected. Verified from the user's own
screenshots on the Nira config: Page blank -> Next greyed; Instagram blank -> greyed; Ad account
blank -> greyed; all filled -> blue. Meta's own docs say the same obliquely ("if you select the
Catalogs asset but don't actually need access to customer catalogs, your customers will likely
abandon the flow at the catalog selection screen"). There is **no per-asset "optional" switch** in
the configuration UI. The only lever is a narrower configuration.

Consequence: a WhatsApp-only customer had **no working path** before this. The unified window
demanded a Page + Instagram + ad account they may not own, and the coexistence button hard-errors
unless the number is already live on the WhatsApp Business mobile app.

**The four configurations (Meta app `2225044871604460`), all system-user / never-expire:**

| Name | ID | Assets | Login variation | Drives |
|---|---|---|---|---|
| Aira - WhatsApp Only | `1063294086656120` | WhatsApp accounts | WhatsApp Embedded Signup | WhatsApp card + the coexistence button |
| Mira - Insta - Facebook | `2226622718102220` | Pages, Instagram | General | Messenger + Instagram cards |
| Nira - Full | `2026693308738446` | WhatsApp, Pages, Ads, Instagram | WhatsApp Embedded Signup | top "Connect Meta Business" panel |
| kira - only Ads | `28328955280071486` | Ad accounts | General | Meta Ads card |

**One config serves both WhatsApp-only and coexistence.** Coexistence is switched on by the
login-time `extras.featureType`, not by the configuration — so `1063294086656120` runs plain
WhatsApp onboarding without extras and connect-without-switching with them. `resolveMetaSignupCompletion`
therefore checks "did Meta open the flow we asked for" (coexistence has its own `FINISH_...` event;
every other mode ends on `FINISH`), NOT mode equality — an earlier mode-equality check would have
rejected `whatsapp_only` outright.

**Why WhatsApp cannot share a hook with the rest.** `useMetaSignup` cannot finish until Meta posts
the `WA_EMBEDDED_SIGNUP` browser message — `MetaSignupCoordinator.takeReady()` needs both the OAuth

separate hook that completes off the `FB.login` callback alone.

**Messenger and Instagram are one connection, not two.** Instagram DMs ride the linked Page's
token (`complete_meta_business_login` reads `page.instagram_business_account` and reuses
`page["access_token"]` for `instagram_access_token`). One Page signup lights up both cards.

**Ads cannot go through the Page endpoint.** `/facebook/business-login/start` raises 400 when the
signup granted no Page, and `/complete` requires a `page_id` with a Page access token. Meta Ads
needs nothing from a Page at runtime — `meta_ads_insights_sync.py` reads only `meta_ads_access_token`
+ `meta_ads_account_id` — so ads-only got its own `/meta/ads-signup/{start,complete}` pair with its

**Ad-account discovery still runs through `debug_token`.** Same SYSTEM_USER problem as the 2026-08-14

## WhatsApp sender selection has TWO sources of truth (2026-09-08)
- **The `phone_numbers.role` column and the `meta_phone_number_id` app_setting are independent answers to "who sends?", and both must be kept pointing at the same number.** Bulk paths (`broadcast_executor.py`, `upload.py`) ask the pool via `outbound_router.get_best_number`, which returns the row with `role="primary"`. Everything else calls `send_text_message`/`send_template_message` without a number, and `meta_cloud._creds()` then falls back to the `meta_phone_number_id` setting. Change one without the other and outbound silently splits: broadcasts go out on the old number while AI replies go out on the new one, with no error anywhere.
- **Inbound replies are the deliberate exception and use neither.** `webhook.py` passes `phone_number_id=meta_phone_number_id` (the number the message *arrived* on) straight into `generate_reply`, bypassing both the pool and the fallback setting. So a customer who messages a standby/locked number gets replied to from that same number — correct, since replying from a different number would break the thread on their phone. Don't "fix" this to force the primary.
- **`compute_unlocked_ids()` unlocks nothing at all when no row has `role="primary"`.** A tenant's first number must therefore always be promoted, or the whole pool sits locked and the connection is dead on arrival. This is why signup can't just always land numbers as standby.
- `numbers_pool` quota does not hide numbers. `GET /numbers/` returns every row tagged `locked: true|false`; the frontend renders locked rows with a dashed border and an amber "over quota" banner. Locked means *cannot send*, not *invisible*. And a locked number can always be unlocked for free by making it primary — the primary slot is guaranteed regardless of quota, so quota only limits running **several** numbers at once, not swapping which one sends.

## Deal lifecycle — intake_sessions (R1–R4, 2026-09-30)
- **Two clocks, don't mix them.** `payment_link_expires_at` only kills the *link* (`expire_intake_session` clears it; deal stays open). `last_activity_at` drives the idle *close*. Only a lead message (text or media) or real deal progress resets it. `updated_at` is never written, so don't use it.
- **One current plink.** `razorpay_payment_link_id` is the only link that counts. Sending a new link cancels the old one on Razorpay (`cancel_payment_link(plink_id, tenant_id)`). Webhooks for any other plink are ignored.
- **A session counts as "paid" if status == 'paid' OR `razorpay_payment_id` is set.** A second payment on a paid deal goes into `extra_payment_ids` through a compare-and-set write (`.not_.contains`). That sets `refund_needed` and alerts staff; staff refund it by hand.
- **Three different 48 h / expiry things existed.** (1) The link expiry. (2) The old 48 h idle cancel, now replaced by `deal_idle_close_days`. (3) The paid → resolved auto-resolve. That last one still exists, but no longer blocks a repeat booking because of `new_booking`.
- **`mark_lost(..., only_from=...)`**: the webhook path passes ("quoted","awaiting_payment") so a late event can't flip a won deal to lost.
- **Idle sweep reads the setting strictly** (`get_setting_strict`). If the read fails, it skips that tenant and never falls back to a default. A DB blip must never mass-close deals.
- **Eval harness:** `backend/evals/conversations/` (`run_aira.py --files scenarios_returning.json`, score with `python -m evals.conversations.returning`). `write_guard.py` makes it refuse DB writes. It needs a tenant key and explicit user OK to spend it.
